# MAGI 模块总结 009：通用计划与可选约束

日期：2026-10-30。本轮修正 008 将时间规划类别强制用于所有计划的问题。

## 1. 修改后的边界

通用计划的主体是行动、完成条件、决策理由、依据、假设和待确认事项。时间和活动分类是可选信息，不再把所有场景归入学习、休息或复盘。

| 输入情况 | 生成与校验 | 展示 |
| --- | --- | --- |
| 无显式时间预算 | `minutes` 可省略或为 null；填写时必须是正整数 | 不要求估时，不凭空补时长 |
| 有 `time_budget_minutes` | 每步必须填写正整数分钟，总和不能超预算 | 显示预算核对 |
| `kind` 缺省或为 null | 正常接受，无论是否有预算 | 不显示活动标签；有完整估时时归入“未分类”汇总 |
| 自定义 `kind` | 接受有界非空字符串，例如“采购比较”“debug” | 按原标签展示与汇总 |
| 只有部分步骤估时 | 无预算时允许，有预算时拒绝 | 明确“部分步骤未估时，未核对总用时”，不显示完整合计 |

旧 `work/rest/review/buffer` 标签仍可读取，保留原来的中文展示，但不再构成枚举限制。旧候选缺少标签不会被误判为不完整；历史已保存正文也不重写。无需数据库迁移。

例如，“比较两个采购方案，列出取舍和缺失报价”可以只有行动和完成条件；不必虚构预计分钟，也不必选择 `rest` 等类别。用户明确给出时间预算时，才启用相应的必填和算术约束。

## 2. 内容歧义怎样处理

保留 008 的用户原文摘录核对、模型假设和待确认事项。综合提示改为通用的约束、行动及完成条件一致性检查，不再要求每种活动按固定时间类别拆分。

程序检查可确定的字段、来源和预算；模型生成阶段提示其检查矛盾并暴露不确定性；用户通过阅读、确认及后续执行反馈修订方案。没有新增自动评审模型，仍然最多四次调用，没有自动重试或修复。

**自定义标签不证明含义正确，原文匹配不证明事实真实，分钟相加也不证明行动可行。** 本轮解决的是通用性和兼容边界，不是声称消除了自然语言歧义。

未来增加金额或依赖校验时，应针对用户实际声明的约束增加可选能力，而不是给所有计划强制加字段。本轮尚未实现金额预算、依赖图或通用约束插件系统。

## 3. 验证总结

```powershell
.\.venv-harness\Scripts\python.exe -X utf8 -m pytest -q
```

结果：**259 passed，15.92 秒**，一个已有 Starlette/AnyIO 弃用警告；七个变更 Python 文件 Ruff 检查与格式检查通过。

本轮调整了此前“分类必填”和“无预算也必须估时”的测试预期，并增加跨场景回归，验证：

- 采购比较、接口排查、出行需求允许不填分钟，自定义标签或无标签均能产生候选。
- 显式预算仍拦截缺少分钟和超预算；标签缺失不影响预算核对。
- 可选分钟仍拒绝布尔值、数字字符串、小数和非法数值。
- 部分估时不显示完整合计，旧候选及显式 null 可正常读取。
- 无时间字段的候选可以确认保存、重建服务后读取、修订为 v2，并保留 v1。
- 独立评测脚本按是否提供预算应用对应检查，不再强制四类活动标签；来源摘录核对继续有效。
- 原有带完整分类的时间规划样例、引用失败拦截及全套已有功能继续通过。

记录：[009 兼容性证据](validation/009-compatibility-evidence.json)，包含通过 `Council.run` 的两个模拟示例。008 的原始证据保留为历史，不作为当前强制约束说明。

本轮没有可用千问密钥，没有请求真实模型、运行本地模型或新增浏览器实测。因此上述结果证明离线程序行为及存储兼容性，不代表真实模型建议质量或云端稳定性已验收。

## 4. 阅读顺序与下一步

先读 `service.py` 的 `Step`、`check_content` 和 `candidate_body`，观察可选字段与预算条件；再读 `generation.py`，观察模型生成 schema 如何仅在有预算时要求分钟。

阅读重点：为什么“没有填写时间”不一定是错误？为什么“有预算但缺少步骤用时”必须拒绝？为什么活动标签可以自由扩展，却不能当作语义正确的证明？
