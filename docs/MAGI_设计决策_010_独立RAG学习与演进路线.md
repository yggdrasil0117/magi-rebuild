# 设计决策010：MAGI独立RAG学习与演进路线

日期：2026-11-01。状态：用户已确认。本文取代[设计决策009](MAGI_设计决策_009_Yggdrasil检索复用边界.md)中“下一步由MAGI调用Yggdrasil检索服务”的实施方向；009的代码审查、测试结果和风险发现继续作为参考证据，不删除、不改写为已经接入。

## 1. 背景与目标

MAGI的长期目标是成熟可用的个人Agent，当前仍按最小MVP逐步推进。用户进一步明确：开发MAGI也用于亲自理解Agent和后端的关键机制；Yggdrasil的RAG主要由Coding Agent实现，用户没有完整参与设计与实现，因此直接把它作为MAGI的检索黑箱，不满足这一学习目标。

MAGI将独立走一遍RAG的核心链路，理解文档版本、分块、检索、证据快照、引用和内容质量边界。这里的“独立”指代码、运行、数据和启动不依赖Yggdrasil，不意味着一次重建完整企业知识库，也不意味着拒绝成熟组件。

## 2. 决策

1. MAGI建立自己的RAG能力，首个实现为本地轻量检索；Yggdrasil只作为设计参考、失败案例来源和评测对照，不是运行依赖。
2. 定义MAGI内部的`RetrievalProvider`接口。该名称表示依赖倒置的能力边界，不等于Yggdrasil适配器；三人格、网页和评测只依赖统一请求与结果，不了解具体数据库和服务。
3. 首个Provider复用MAGI已有有界文件搜索的安全边界，并逐步加入文档身份、版本、分块、关键词/BM25检索和不可变证据快照。是否使用SQLite FTS5等成熟组件，在实现轮先验证本机可用性和接口边界。
4. 当前阶段不复制Yggdrasil的Java代码、数据库迁移、企业租户/密级、异步摄取、BGE部署或证据包表；可以借鉴经过验证的原则，并重新写出MAGI场景下可理解、可测试的实现。
5. 本地4B生成模型和本地嵌入模型都不自动启动。第一阶段先建立可解释的关键词基线；向量召回使用可替换的Embedding Provider，只有在固定评测证明关键词不足且用户选择资源方案后接入。
6. RAG仍是MAGI的支撑能力。产品主线保持“个人目标与约束 → 三人格权衡 → 用户确认 → 行动计划 → 执行反馈与修订”，不转向通用企业知识库平台。

## 3. 边界与解耦

```text
普通聊天 / 三人格审议 / 固定评测
                ↓
       MAGI RetrievalProvider
                ↓
      MagiLocalRetrievalProvider
                ↓
  文档版本 → 分块 → 检索 → 证据快照
```

未来可以增加`YggdrasilRetrievalProvider`、MCP Provider或云端知识库Provider，但都是可选实现。MAGI的启动、普通聊天、本地资料和三人格核心流程不能要求Yggdrasil在线。

统一结果至少需要表达：检索状态、原文片段、MAGI文档ID、文档版本ID、分块ID、原文位置、内容摘要、检索方法和覆盖/截断说明。上述ID属于MAGI资料域，不复用Yggdrasil的sourceId、workspaceId或企业身份，也不能与turn_id、memory_id、plan_id、计划版本和operation_id混用。

`RetrievalProvider`负责候选检索和结构化返回；证据快照层负责冻结本轮实际原文；三人格负责依据材料分析；程序检查引用是否来自本轮快照；用户决定是否保存计划。候选非空、结构校验通过、流程COMPLETED和用户确认仍是不同事实。

## 4. MVP实施顺序

下一开发轮只完成一条最小但完整的资料审议链路：

1. 定义Provider请求、结果、失败状态和预算。
2. 建立最小文档/版本/分块表示，继续限定授权本机文本资料范围。
3. 实现可解释的关键词或BM25检索基线，不预先加入向量数据库。
4. 将本轮实际片段冻结为证据快照，三个角色读取同一份证据。
5. 三人格只能选择已有证据编号；程序还原原文并拒绝自造引用。
6. 计划确认后保留当时使用的证据版本；资料后来变化不能静默改写旧计划依据。
7. 页面以普通用户可理解的方式显示来源、版本、原文、无结果和失败；内部ID按需收起。

这是一轮功能实现与验收，不继续只写框架空壳。具体数据库表、分块长度、FTS5/BM25组件选择和页面形态，由执行轮根据现有代码做最小设计并留下中文注释。

## 5. 最小验证与升级条件

固定案例至少覆盖：原词命中、同义改写、资料无答案、同文档新旧版本、文件变化、检索失败、伪造引用和重启恢复。分开记录程序正确性、召回/排序、引用支持、三人格内容复核、延迟与模型成本；保留所有尝试。

首轮的目的不是证明关键词检索生产可用，而是得到可重复基线。后续按照证据升级：

```text
有界字面搜索
  → 文档版本与分块
  → SQLite FTS5/BM25基线
  → 可替换云端或本地嵌入Provider
  → 关键词/向量融合与重排
  → 规模、质量、监控和故障降级
  → 账号隔离、生产数据库和多实例部署
```

同义改写失败是评估向量召回的证据，不是允许模型补写来源；向量失败时是否退回关键词必须由程序显式标记。生产级目标保留，但每一阶段必须先有当前规模下可解释、可复现的收益。

## 6. 与Yggdrasil的关系

第25轮确认Yggdrasil在权限过滤、证据完整性、版本风险和混合检索方面有参考价值；这些结果继续用于设计检查和相同题目的对照。MAGI不会复制其完整实现，也不会把其历史评测算成MAGI成绩。

两个项目允许共享RAG通用概念，但产品重点不同：Yggdrasil展示企业资料治理、权限检索与证据问答；MAGI展示个人上下文选择、三人格共享证据、决策取舍和计划演进。未来若抽取公共包或接入外部Provider，必须在MAGI独立实现和基线验收之后另作决定。
