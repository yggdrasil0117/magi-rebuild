## 1. 产品定位与目标

> MAGI 是面向学习、研究与创造的长期个人 AI 助手。它围绕用户持续推进的事情保留上下文，通过自然对话提供陪伴与建议，并调用工具完成可检查的任务；遇到重要取舍时，可以启用 EVA 三人格共同审议。

首批用户是项目作者本人及有相似需求的研究生、开发者。第一版聚焦学习、科研与求职场景，长期愿景允许跨领域扩展。陪伴体现为稳定自然的交流、延续已确认的上下文和尊重用户的变化，不要求每次聊天都制定计划或启动工具。

| 主线 | 目标与边界 |
| --- | --- |
| 个人产品 | 用户能在同一个入口聊天、共同思考、整理资料和推进事项 |
| 工程与求职 | 展示模型适配、上下文与记忆、任务状态、工具执行、持久化及验证能力 |
| 研究能力 | 在软件任务中研究有效规约、补丁符合性与证据追溯，独立维护实验数据与评价 |

软件开发和验证成为专业能力。它可以使用开源 Coding Agent 执行底座，但不再决定整个个人助手的身份。通用助手演示不作为论文效果证明。

## 2. 核心用户故事

用户说：“最近论文和求职挤在一起，帮我理一下。”助手结合已确认的背景讨论优先级，不自动执行任务。

用户接着说：“读这两份材料，整理本周三件事。”助手读取授权资料，产生带来源和未知项的建议。

用户说：“把这个计划保存下来。”程序保存计划，回读核对后在原对话确认。用户已明确要求该次保存时，不重复请求同一授权。

关闭并重新启动应用后，用户说：“昨天第二件事是什么？今天只有一小时，帮我调整。”助手从实际保存的计划读取内容，结合新的时间约束提出修改。更新后的版本替代旧的有效版本，历史修改仍可追踪。

用户遇到取舍时说：“让三人格帮我权衡。”系统执行有预算的独立分析和汇总，最后由用户决定是否把建议转为行动。

这个故事是第一版的主要验收入口。跨天可以用明确记录日期与重启测试验证，不要求人为等待一天。

## 3. MVP 范围

| 必须完成 | 后续扩展 |
| --- | --- |
| 单用户、连续文本对话与重新打开会话 | 多租户、语音、桌面控制和移动端 |
| 可查看、更正、删除的少量已确认记忆 | 自动大规模记忆抽取、向量记忆与复杂衰减 |
| 资料读取、整理，笔记与计划保存及查询 | 邮件、日历等外部写入和主动定时跟进 |
| 简单任务状态、结果与事件持久化 | 分布式调度、高并发、无人值守长任务 |
| 用户主动启用的三人格审议 | 自动判断何时启用、多模型动态调度 |
| 模型配置集中、接入边界可替换 | 多提供方自动容灾、复杂成本路由 |
| CLI 验证核心行为，最终有简洁会话界面和记忆/结果入口 | 完整产品工作台与装饰性 EVA 动效 |

文本资料先覆盖当前 UTF-8 文件能力。PDF、Office 等格式按真实需求复用已有转换组件，不能让通用格式支持阻塞主线。

完成 MVP 不以“修好一个代码缺陷”为必需条件；软件规约与补丁验证是后续专业模块。产品仍必须完成真实保存、查询和更新，不能仅输出声称已操作的文本。

## 4. 统一对话中的行为边界

前台保持一个会话入口，后台按请求组织三类行为：

| 行为 | 触发与产物 |
| --- | --- |
| 对话与思考 | 闲聊、解释、倾诉和建议；可以自然回答，不强制输出 JSON 报告 |
| 任务执行 | 用户明确要求读取、生成、保存或更新；创建任务，执行并核对结果 |
| 三人格审议 | 用户主动请求权衡或审议；产生观点、分歧、依据与建议，不自动授权写操作 |

意图识别可以使用模型，但“建议”不能自动变成写操作。模型返回的动作请求要经过程序参数与权限检查。需要确认的动作记录目标、参数和版本；这些信息改变时原批准不能继续沿用。

MVP 的操作范围是用户授权资料和专用笔记/计划存储，聊天不默认获得任意文件写权限。没有接入定时服务前，不承诺稍后主动提醒。

对话历史保留用户表达和工具结果，但不得把历史任务、文档中的指令或模型生成的计划当作新的用户命令。

## 5. EVA 三人格的职责

| 人格 | 判断侧重 | 对用户的作用 |
| --- | --- | --- |
| MELCHIOR | 证据、逻辑、条件与可行性 | 检查事实依据，提出可验证的行动 |
| BALTHASAR | 人的负担、成本、影响与可逆性 | 识别时间压力、副作用与恢复代价 |
| CASPER | 用户意愿、自主性与长期价值 | 检查建议是否符合本人目标及偏好 |

这是 EVA 灵感的软件产品改编。人格不固定支持或反对，不必强行产生分歧，不把投票数量作为真理保证。

首轮共享任务快照、已确认背景与证据，分别分析，互不读取初始结论；可以串行调用以控制本地资源。随后汇总共识、异议和待确认项。普通聊天不默认调用三个模型。

MVP 首先完成一次独立分析加一次汇总；是否增加交叉复核取决于具体任务，不能直接照搬旧 A/B 领域的“两轮投票”作为全部任务规则。预算耗尽或人格失败时明确报告不完整，不伪造意见。

审议结果不直接操作存储；用户接受某项行动后，由统一任务执行入口处理。评估时检查三人格是否改变了建议或验证动作，并与单 Agent 比较耗时和成本。

## 7. 目标架构与后端职责

```text
统一会话入口（先 CLI，后简洁界面）
    ↓
应用服务：上下文组装、任务路由、记忆管理、按需审议
    ├─ 会话 / 记忆 / 计划 / 任务 / 事件存储
    ├─ Deep Agents 试验接入（原 runner 保留为学习对照）
    │    ├─ 模型适配：本地 Ollama / 后续 API 服务
    │    └─ 工具执行：资料、笔记计划、后续专业能力
    └─ 验收：操作结果、引用边界、未解决事项
```

界面、模型接入和执行底座均不直接拥有业务状态的最终解释权。事实以持久化记录和核验结果为依据。普通回答可以是文本；工具调用和业务结果使用明确的数据结构。

建议的最小数据对象（字段和接口在模块实现时明确）：

| 对象 | 最小职责与关联 |
| --- | --- |
| Conversation / Message | 会话 ID、顺序、角色、时间、正文和工具结果关联 |
| Memory | 内容、来源消息、确认状态、版本及失效信息 |
| Task | 会话关联、用户目标、参数快照、运行状态和结果 |
| Note / Plan | 用户保存的内容、版本、来源和修改记录 |
| ToolCall / Event | 任务关联、调用身份、结果状态及必要诊断信息 |
| Evidence | 任务内编号、来源路径、内容版本；跨任务使用需组合任务 ID |

阶段一先用 SQLite 验证单用户持久化；若复用评估表明现有 PostgreSQL 组件更合适，再记录选择原因。无需一开始引入消息队列或微服务。

任务状态草案：`CREATED → RUNNING → SUCCEEDED`，并支持 `WAITING_FOR_USER`、`FAILED`、`CANCELLED`、`INTERRUPTED`。状态定义应对应操作结果，不能直接把 `run_completed` 映射为 `SUCCEEDED`。重启后未完成任务先标明中断，写入结果未知时先核对，不默认重放。

写入采用任务/操作标识去重，计划修改绑定版本。重复提交、取消、失败后查询都是 MVP 的工程验收范围；自动续跑不是前提。

## 8. 会话与可管理的记忆

对话历史、记忆和任务结果分别存储。历史表达不自动成为有效记忆，模型的推测不直接成为用户事实。

- 用户明确说“记住我偏好……”时，可按明确请求保存；从普通聊天推测出的候选先等待确认。
- 允许查询、更正和删除记忆，记录来源与版本，保留必要的变更事实。
- 新会话只检索当前有效记忆；更正或删除后，摘要、缓存及检索结果不能重新注入旧内容。
- 旧聊天记录即使保留供用户查看，也不应把已经撤销的偏好重新送给模型作为当前事实。物理历史清理与有效记忆删除需在界面说明区别。
- 冲突未明确解决时，保留不确定性并询问；不能简单以较新时间覆盖不同作用域的要求。
- MVP 先使用少量结构化确认项与显式任务记录，不依赖向量库才能跨会话延续。

上下文组装遵循预算：保留本轮请求、有效约束、关联任务结果与必要证据，按需读取历史。摘要是辅助上下文，不能取代原始任务结果或擅自提高事实权威性。

## 9. 模型切换、SDK 与既有项目复用

模型配置应集中表达：提供方、模型名、服务地址、密钥环境变量名、超时、上下文和生成预算。密钥不进入代码、普通日志或示例配置；实际费用只在计价和用量可靠时报告。

Ollama 的 `think`、`format` 以及响应对象形态应封装在接入适配中。应用层表达“文本生成、工具请求、结构化结果”等需要，由适配层实现或明确报告不支持。不能默默丢弃工具或结构化输出要求。

模块 003 已接通当前 Ollama，后续用一套相同能力测试接第二个 API 提供方；用户尚未提供服务信息，因此不锁定名称或承诺兼容。切换配置不意味着模型理解能力相同，必须记录任务成功率、延迟与成本差异。

保留现有 runner 作为学习和对照实现。用户确认优先复用后，模块 003 已验证 Deep Agents 的短对话、原有文件工具及跨进程恢复，新增主线以该接入为起点；没有证明质量或性能优于旧 runner。版本锁定、权限和调用预算由应用实际校验。OpenHands 等 Coding Agent SDK 仍为软件专业能力的候选，不作为整个个人助手的既定核心；此前“先接 OpenHands 做完整 MVP”的建议被本版路线替代。

用户简历中的“企业知识与行动 Agent”描述了记忆、MCP、审批、任务恢复和 Java 后端。它是复用候选，当前未审查对应仓库，不能直接声称已迁入。先盘点可独立复用的接口与模块，再逐项决定；不整仓覆盖 MAGI，也不为保留某种技术栈拆出无必要服务。

## 10. 资料、证据、RAG 与能力扩展

保留现有来源编号、内容哈希和报告验收。区分三个层次：引用指向已读取内容、结论受到原文支持、资料适用于当前问题；目前只对第一层和结构做了确定性检查。

针对有明确权威资料的任务，可用小型资料清单记录文档类型、日期、适用范围与替代关系；不强制为个人助手建立复杂的通用规约图。普通聊天不要求提供引用，基于资料的事实性结论需要来源，无法支持的部分明确列为未知。

RAG 按原 TXT 规划作为工具能力：先有界文件与关键词搜索，再按需要加入 BM25、向量召回和重排序。嵌入 API 或本地选择以效果、资源和成本实验决定。嵌入失败且有关键词索引时允许降级并标记，不把无结果变成已验证答案。

多格式转换评估 MarkItDown 或现有项目组件；保留来源与解析失败。MCP 接入复用同一动作边界与结果检查，不因协议接通就授予全部操作权限。

首个写工具优先保存笔记/计划到专用存储并回读验证。软件文件修改、测试执行与 Docker 工作区作为后续专门能力，不能因为已有文件读取就开放任意 shell。

## 11. 软件研究能力的独立边界

开题研究单位是需求时点 t、仓库版本 v、AI 补丁 P 及可获得轨迹 H；有效规约附带来源、适用范围、冲突与缺口。专业能力按约束输出“违反／已支持／未知”，并绑定实际补丁与验证条件。

软件研究模块保留原设计中规约演化、最终版本验证、过程证据关联等需求。日常偏好更新可借鉴来源与失效处理，但不能声称通用聊天记忆就是论文方法，或以个人助手演示代替独立评价。

研究数据、开发样例与独立评价分开。已有已知失败案例用于开发，不重复作为独立效果证明；三个方向是否具有创新和增量收益仍待研究验证。MVP 不要求论文方法全部完成。

## 12. 验收与失败策略

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| PA-01 | 普通解释或日常聊天 | 能自然连续交流；未明确要求行动时不执行写操作，也不默认三人格调用 |
| PA-02 | 退出后再次打开同一会话 | 从持久化历史与关联结果恢复上下文，不能靠进程内列表冒充持久化 |
| PA-03 | 记住、修改、删除一个偏好 | 查询结果与用户操作一致，失效项不再进入新的模型上下文 |
| PA-04 | 读指定资料并保存计划 | 记录实际来源；收到保存请求后写入并回读确认，输出可查询的结果标识 |
| PA-05 | 次日调整计划 | 找回正确计划与版本，按新要求修改，不凭模型记忆编造旧内容 |
| PA-06 | 重复请求、写入异常或重启 | 无重复产物；结果未知则核对或标明中断，不能直接报告成功 |
| PA-07 | 主动启用三人格 | 首轮上下文隔离、有预算、意见可追踪；分歧与未知可见，行动仍经任务入口 |
| PA-08 | 切换模型配置 | 不修改产品业务逻辑；当前提供方通过能力测试，第二提供方未接入时如实标注 |
| PA-09 | 工具失败或预算不足 | 保留已完成结果及失败状态，不伪造工具返回或审议意见 |
| PA-10 | 资料过时、来源不支持 | 不因引用合法就宣称事实成立；在固定验收样例中识别时点冲突或报告不足 |

模型超时可在明确预算内重试；有副作用调用必须先核对执行状态。任务预算应覆盖调查、报告生成和三人格等全部阶段，不能只统计 runner 内部请求。新模块逐步实现这些规则。

产品评估记录跨会话续接成功率、错误记忆召回、保存/更新正确率、任务完成情况，以及用户实际使用反馈。三人格采用相同任务与可比预算的对照，不能先宣称质量更高。
