# 网页核心改造兼容验收

网页现在由自有聊天循环执行工具，并把完整消息批次和轮次状态交给同一个业务事务保存。验收从现有工作区出发，保留模块036和037的原有改动。第035轮的摘要和语义记忆需要在新入口上验证，因为旧图入口的测试无法证明新聊天循环传给模型的内容。

新增 tests/test_native_chat_memory.py，走默认 WebService，使用脚本模型查看实际输入。第一个用例创建四轮长聊天，每轮重新构造服务。第四轮送入摘要与第二轮起的近期原文，网页历史仍可读取第一轮。第二个用例使用真实 SQLite、本地 Qdrant 和固定向量替身。将每周10小时改为4小时并重新构造服务后，模型输入和页面来源记录均使用版本2。

第一次摘要试验使用 8192 字节容量，第三轮先触发容量守卫，尚未到可压缩的第四轮。将测试容量改成 16384 字节，并配合每条 1450 字符的合成输入后，验证了压缩路径。生产配置及容量守卫未改。该结果表明较小预算下工具规格和消息序列化开销可能先耗尽容量。若后续改善这一行为，应让摘要触发使用与最终容量守卫一致的估算，并保留完整轮次边界。

完整基线命令为 .venv-harness/Scripts/python.exe -m pytest -q --basetemp .magi/test-core-rebuild，455 项通过，3 条依赖弃用警告。新增用例单独运行 .venv-harness/Scripts/python.exe -m pytest -q tests/test_native_chat_memory.py --tb=short，2 项通过。本轮没有重新调用云端或浏览器，也未执行真实进程中断。重新构造服务验证数据库读取，和操作系统进程重启分开记录。
