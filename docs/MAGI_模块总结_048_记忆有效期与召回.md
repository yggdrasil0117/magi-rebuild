# MAGI 模块048：记忆有效期与召回

2026-11-10

你这周只有 4 小时复习时间，下周的安排还没定。如果把“每周可学习 4 小时”保存为长期记忆，MAGI 下周也可能沿用它。现在可以在个人记忆里保存“本周可学习 4 小时”，同时选择截止时间。之后到达该时刻，新请求跳过这条记忆。管理页仍保留原内容，你可以核对后续期、清空截止时间或删除。

## 从页面确认到数据库

添加或修改时，网页以浏览器本地时区显示时间，并把新时间转换为明确的 UTC 时刻。预览冻结正文、截止时间和 `request_id`，点击确认后才发出写请求。API 要求带时区的截止时间，业务服务会再检查它晚于当前时间。省略更新字段时保留原日期，传 `null` 则恢复为长期有效。这一区分让旧客户端和记忆建议的确认仍能只更新正文。只改正文不会悄悄续期。

下面是 [MemoryService._change](../src/magi/personal/memory.py) 在事务中检查旧版本后执行的有效期判断，后面接数据库更新。

```python
if "expires_at" in data:
    _require_future(data["expires_at"], now)
expiry = None if deleting else data.get("expires_at", row["expires_at"])
```

`data` 包含从已确认请求归一化出的变更，`now` 是程序当前的 UTC 时间，`row` 是数据库里读取到的原记录。用户续期时，事务将截止时间与新版本同时提交，并记录操作回执。原有触发器会为新版本登记索引待办。记忆 ID 标识这条事实槽位，续期沿用 ID 并增加版本，`request_id` 标识一次具体操作。后台先检查是否已经处理过同一请求，再检查新期限是否过期。因此即使第一次响应丢失，到期后重复同一个已成功请求仍得到原回执。旧版本提交则返回冲突，用户需要刷新后核对。

数据库从 v13 升级到 v14 时添加可空列。旧记录的截止时间为空，仍长期有效。过期状态由读取时的时间计算，不会删除记录、改写版本或登记一次虚构的用户操作。到期的记录仍保留原名称槽位，要重新使用时可从管理页续期。这也避免用相同名称创建新记录时，旧记录后来恢复又发生冲突。

## 一条规则供各入口使用

[memory.py](../src/magi/personal/memory.py) 定义实际生效的查询条件。

```python
EFFECTIVE_MEMORY = "status='ACTIVE' AND (expires_at IS NULL OR expires_at > ?)"
```

SQL 参数是本次查询的 UTC 时刻。截止时间等于当前时刻时就排除。普通聊天在读取记忆时先应用此条件，再按会话范围和同键优先规则选择。因此会话专属记忆一旦过期，仍有效的同名全局记忆可以继续用。三人格审议走同一上下文读取，独立研究和共同聊天室则继续只选公共记忆，再排序和截取候选。管理页单独列出所有未删除公共记忆并显示服务端计算的到期状态。

语义召回也从这批有效记录计算允许的记忆 ID 和版本。旧向量即使物理上还在 Qdrant，也不在查询允许列表里。召回后和组装聊天提示词前会再次核对当前有效记录，处理检索期间到期的情况。续期写入新版本后，新一轮语义召回补建索引，旧版继续被排除。SQLite 保存用户确认的事实和期限，Qdrant 保存可重建索引，MAGI 负责把范围、时效和版本带入查询。到期不需要常驻后台任务。

已经提交给模型的请求、历史聊天或旧报告可能仍包含当时有效的正文。到期过滤针对新请求中的记忆注入。它不改写历史内容，也不会清除磁盘上的过期向量。若用户需要删除记录，可继续使用管理页原有删除流程。

## 面试知识关联

这里的业务问题是“期限过去后立即停止使用”。它对应读取时效校验和业务库与派生索引的一致性。我们让读取时钟参与数据库过滤，再限制向量查询的 ID 和版本，所以就算删除向量的操作尚未发生，也不会召回过期内容。若被追问为什么不只做定时删除，可以用“清理任务迟到十分钟”举例，解释为什么定时清理无法独立承担请求的时效边界。若要做通用遗忘，还需要定义哪些内容可自动归档、怎样撤销以及如何验收误删。本轮没有加入这些策略。

建议先在使用指南走一遍新增与续期，再读 `MemoryService._change`、`ContextService.build_current_context` 和 `recall`。之后可自查两个问题。过期和删除对数据库的影响各是什么？为什么即使 Qdrant 还持有旧向量，也只能返回符合 SQLite 当前版本的候选？
