# 设计决策 002：独立产品、学习主线与服务边界

日期：2026-10-29。状态：根据用户最新说明更新开发基准；本文明确定位和实施边界，不是功能完成报告。

## 1. 决策背景与优先级

早期 Yggdrasil 与 MAGI 主要由 Coding Agent 实现，用户对内部机制了解有限。本次重构的核心目标，是让用户掌握 Agent 和后端开发，拥有可以理解、维护并长期迭代的 MAGI。求职展示、向 Yggdrasil 提供服务、后续面向其他用户，都建立在这个基础上。

因此，不能只以最少新增代码为目标，把 MAGI 缩成另一个项目的薄插件；也不能以学习为由重新实现所有通用组件。优先级为：独立可用且核心流程可理解 → 完整产品闭环 → 持续迭代 → 其他系统集成。一周目标仍是第一份可演示雏形，不能等同于长期产品完成。

## 2. 产品定位

> MAGI 是具有三人格审议能力的个人决策与行动助手：围绕持续目标理解用户背景，比较方案与取舍，把认可的方案转化为行动计划，并根据执行反馈和约束变化复盘调整。

首批场景是用户自己的学习、科研和求职。日常陪伴体现在交流自然、记得已确认背景、能够延续同一件事；不是每次闲聊都要求制定计划。未来跨领域能力通过具体工具扩展，不以“什么都能做”作为首版验收标准。

三人格是 MAGI 的特色交互和推理流程：MELCHIOR 关注依据与可行性，BALTHASAR 关注负担与影响，CASPER 关注自主选择与长期目标。三者独立分析同一问题，再综合共识与分歧。它们可以使用同一模型；人格名称和提示词本身不构成质量优势，需要真实案例验证。

三人格给出的动作建议统一进入执行服务。工具能做什么、什么时候可以写入、失败后怎么恢复，由程序管理，不给每个人格随意操作系统的权限。后续需要人格专属工具时，再增加明确的能力边界。

## 3. MAGI 与 Yggdrasil 的关系

MAGI 保持独立仓库、服务入口、启动方式和直接面向个人的使用路径。Yggdrasil 是潜在调用方之一，而不是 MAGI 的必需运行环境。

| 项目 | 主要产品责任 | 可重用/协作部分 |
| --- | --- | --- |
| MAGI | 个人对话、有效记忆、目标与计划、三人格、受控行动 | 向外部提供审议和任务能力 API |
| Yggdrasil | 知识资料管理、权限检索、证据问答与企业工作流 | 提供经授权的证据快照，接收 MAGI 审议结果 |

两边都有普通聊天是可接受的入口重叠。不能仅因入口相同，就认定产品相同或要求迁移核心业务。是否复用已有代码，要看代码是否可理解、边界是否合适、是否能通过测试，而不是只看功能名字相同。

### 3.1 双项目简历的功能边界

用户明确要求两个项目都用于简历，核心功能应有区分。当前 Yggdrasil 已包含普通聊天、记忆、单 Agent 工作台、MCP 与审批，不能把这些能力包装成 MAGI 独有亮点，也不能把 Yggdrasil 描述为只有文档检索的简单 RAG。

| 维度 | Yggdrasil 展示主线 | MAGI 展示主线 |
| --- | --- | --- |
| 核心问题 | 从有权限的资料中找到可靠答案并追溯依据 | 在目标和约束之间作出选择，并根据反馈调整行动 |
| 主业务对象 | 文档、分块、证据包、权限、检索/摄取任务 | 目标背景、候选方案、人格意见、决策理由、计划版本与反馈 |
| 标志性流程 | 上传 → 解析 → 权限检索 → 证据问答 → 引用核验 | 目标/约束 → 三人格权衡 → 用户选择 → 行动计划 → 反馈再规划 |
| 工程贡献重点 | Java 业务边界、异步摄取、混合检索、权限与证据完整性 | Python Agent 编排、上下文选择、人格隔离、有界执行、决策与计划演进 |
| 记忆的用途 | 支持问答和工作台的基础能力 | 延续用户目标、偏好和先前选择，约束变化时重新评估 |

MAGI 首版不建设文件上传解析平台、向量索引、混合检索、知识库管理、企业权限后台或第二套通用 MCP 工作台。需要资料时，先接受用户提供的简短材料和已有只读工具，后续通过适配器使用 Yggdrasil 的授权证据能力。通用聊天、HTTP、日志、持久化属于必要基础，不要求为了区分简历而删除。

原先“聊天、三人格、保存计划”仍不足以充分拉开产品差异，因此补充一个关键验收：用户改变约束或报告执行反馈后，MAGI 对照原计划提出修订，解释保留/放弃了什么，经用户确认产生新版本，并能查询旧版本与修订理由。首版复用现有 PlanService.update，使用明确命令即可，不新增完整任务管理平台或复杂 Goal 聚合。修订理由作为计划修订内容的明确字段/段落保存，不能只留在瞬时模型输出里。

示例：最初“本周六小时，论文与求职并行”形成计划 v1；随后用户报告“实验卡住，只剩两小时”，系统提出 v2，并说明缩减事项与依据。这个持续权衡与反馈流程是 MAGI 的主演示。不得声称三人格必然优于单 Agent；对照案例应检查它是否识别了额外约束，以及增加的耗时是否值得。

简历标题建议分别使用“Yggdrasil：企业知识检索与证据问答平台”和“MAGI：三人格个人决策与行动助手”。描述只写已经实现并验证的贡献；Yggdrasil 调用 MAGI 时明确写成集成，不在两个项目中重复宣称实现了两套三人格引擎。

首周先完成 MAGI 独立用户闭环。随后通过适配层处理 Yggdrasil 的旧 A/B 决策协议与新审议接口差异。外部请求绑定调用方身份、任务和授权证据，不自动读取个人用户记忆；个人上下文与外部项目上下文不得混用。Yggdrasil 的权限、业务事务与执行批准继续由它负责，MAGI 返回建议不能代替其授权。

当前 Yggdrasil 文档里的集成指向旧 `magi`，不是本仓库 `magi重构版`；已有适配位置不代表新协议已接通。集成验收独立记录，不阻塞 MAGI 第一版直接使用。

## 4. 复用和学习边界

| 层 | 当前事实或计划 | 用户需要掌握的内容 |
| --- | --- | --- |
| 模型接入 | 当前为 Ollama + ChatOllama；其他 API 待接入 | messages、工具调用、结构化输出、超时与截断、配置切换 |
| Agent 执行 | 现有 Deep Agents/LangGraph harness；旧手写 runner 保留作学习基线 | 谁发起模型请求，谁执行工具，循环怎样停止，状态怎样恢复 |
| 会话历史 | 现有 SQLite checkpoint | 模型实际看到什么，重启如何恢复，历史与当前事实的区别 |
| 个人记忆 | 自有业务 SQLite、MemoryService、ContextService | 显式确认、作用域、版本、修改删除、epoch 失效与重新绑定 |
| 计划与操作 | 自有 PlanService、版本与 Operation | 事务、幂等、确认内容绑定、真实回执与失败状态 |
| 三人格 | 待实现的 MAGI 业务工作流 | 输入快照、首轮隔离、预算、综合、部分失败和效果评估 |
| HTTP | 待实现的 FastAPI 适配层 | 请求校验、身份、错误响应、业务调用和生命周期 |
| 界面 | v0.3 的 Open WebUI 作为可替换入口 | 只负责交互，调用 MAGI API；不能拥有唯一一份核心业务逻辑 |

当前并非“还完全没有框架”，也不需要再次做整体框架迁移。先把已有 harness 的调用关系讲清楚，再增量实现产品流程。复用框架不等于必须读完框架所有源码；应能指出它负责的步骤、配置边界，以及用什么行为测试证明接入正确。

Open WebUI 方案仍作为首周默认界面选择；它不定义 MAGI 的身份和产品能力。MAGI 的核心验收还应能通过 API/CLI 运行，不依赖特定 UI 插件。如果 UI 接入成为障碍，可先交付简单界面，避免反复更换整个后端。

## 5. 记忆机制必须讲得清楚

当前设计区分三类信息：

1. 对话历史：记录过去说过什么，存在 checkpoint；不是所有历史都永远进入当前上下文。
2. 已确认记忆：用户明确保存的偏好和背景，有作用域、版本与有效状态，存在业务库。
3. 持久计划：用户确认过的产物，有不可变版本和操作回执；不是自动提取的事实记忆。

修改或删除记忆会推进 context_epoch。后续请求解析新的有效会话段，避免旧偏好从历史重新进入推理。界面可以显示旧历史，但不能因此把全部旧文本重新传给模型。计划来源 epoch 过时时标记待复核，不自动把旧正文再次作为模型依据。

这是一种明确、可检查的首版记忆机制，尚未实现向量记忆或自动长期记忆抽取。后续出现真实检索需求时再增加，不能把框架的会话持久化直接称为完整长期记忆。

## 6. 第一版完成定义

继续按 v0.3 的接口、数据边界和验收清单推进，产品必须独立完成：

> 用户提出目标和约束 → MAGI 使用有效上下文 → 三人格审议 → 用户确认计划 → 真正保存 → 重启查询 → 用户反馈或约束改变 → 提出带理由的修订 → 确认生成新版本。

首版行动范围为现有只读资料工具、计划保存、查询及反馈后的版本更新；后续加入代码、笔记、日历等具体工具。计划保存与更新是真实业务动作，不宣称已经拥有通用自主执行能力。

学习交付与功能交付同时进行：每个完整阶段提供一张调用流程图或简明调用链、一份核心文件阅读顺序、一次正常与失败路径说明、一个可选小改动。用户能逐步解释以下问题：

- 一条消息从界面到模型再回到界面经过哪些模块？
- 哪些行为来自框架，哪些规则由 MAGI 决定？
- 当前请求用了哪些历史和记忆，删除之后为何不会回流？
- 模型请求工具与 Python 真正执行工具有什么区别？
- 保存成功的依据是什么，重复请求为什么不会重复保存？
- 三人格实际增加了哪些信息，失败时会发生什么？

这些问题用于讲解和检查理解，不作为阻止开发的考试。维持完整功能阶段的粒度，避免恢复到逐字段、逐行推进。

## 7. 执行顺序与交接修正

1. 先对已有 harness、记忆、计划做一次代码导读，并用临时数据跑通现有路径；输出模块关系与数据流，不重新实现已经工作的基础。
2. 接通独立 MAGI API 与最小界面，让日常聊天可实际使用。
3. 完成三人格工作流、确认保存、恢复查询及必要失败验证，达到完整 MVP。
4. 生成设计对照、运行证据、学习总结和未完成清单。
5. 在独立 MVP 上迭代一个实际使用功能，再接入 Yggdrasil；不同时重构两个项目。

沿用“当前模型先设计，用户切换执行模型后实现”的协作约定。本轮更新设计，不代表已自动切换模型或完成开发。执行模型应同时阅读本文、v0.3 与现有模块总结；本文关于独立产品、上下文隔离和学习目标的决定优先于此前“把 MAGI 缩成 Yggdrasil 插件”的建议。

后续评估新方案时先判断它是否帮助用户拥有一个可理解、可维护的 MAGI，再衡量减少多少代码。定位先保持稳定；真实使用和验收证据推动迭代，不因发现另一个项目也有聊天功能就重新改变主线。
