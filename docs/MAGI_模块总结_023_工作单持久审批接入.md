# 模块023：工作单持久审批接入

日期：2026-10-31。先补充[设计决策008](MAGI_设计决策_008_工作单持久审批接入.md)，再把第22轮验证过的框架能力接到实际工作单流程。

## 1. 本轮可见变化

现在网页准备工作单后，会进入持久待审批状态，显示“批准并创建文件”和“拒绝本次创建”。批准后才创建文件；拒绝状态刷新后保留，不能再批准同一预览。需要改变主意时点击“准备新工作单”，生成新的文档记录，不覆盖旧拒绝。

已创建文件仍可点击核对，重复确认不创建第二份，也不覆盖外部编辑。文件创建不代表工作单里的学习、采购等计划事项已经执行。

重启服务、刷新网页即可使用。仍是本机服务凭据和服务端owner，不是新账号系统；模型不拿凭据决定权限，也不能提交批准或拒绝。

## 2. 复用什么，自己负责什么

第22轮用Deep Agents的工具审批验证通用机制。本轮动作已经明确为“创建这份工作单”，因此直接复用其底层**LangGraph StateGraph、interrupt、SqliteSaver**，不额外调用模型去再选择一次工具。没有把试验脚本模型接到产品，也没有升级框架依赖。

```text
页面按钮或模型工具准备预览
→ TaskDocuments保存冻结内容
→ LangGraph进入等待决定节点，checkpoint持久保存中断
→ 页面展示预览和批准/拒绝
→ 后端核对凭据对应owner、文档、摘要、当前中断
→ 先持久保存用户唯一决定
→ Command恢复框架
→ 执行节点调用已有TaskDocuments.confirm，或拒绝后不执行
→ 页面展示真实业务结果
```

框架负责暂停、保存位置和恢复；MAGI负责身份、内容绑定、决定冲突、业务一致性与页面；原TaskDocuments负责文件原子发布、不覆盖与重复核对。不是重写一套Agent循环或暂停引擎。

执行图只含确定性状态与两个节点，不包含模型消息，**审批本身新增模型调用为0**。用户自然语言准备预览仍按第20轮通过模型工具完成；原生网页开启自动记忆建议时的额外分析规则没有改变。

## 3. 保存在哪里，ID怎样区分

业务schema从6升级为7，新增`document_approvals`表：文档编号、owner、冻结摘要、当前中断编号、唯一决定和安全错误码。业务库同目录增加独立审批checkpoint，例如默认业务库`personal.sqlite3`对应`personal.approvals.sqlite3`。备份或迁移时应一起保留；没有自动清理或归档功能。

| 对象 | 作用 |
| --- | --- |
| document_id | 已冻结的工作单预览/产物，不是新的计划版本 |
| payload_hash | 用户确认的完整内容摘要 |
| interrupt_id | 当前待审批暂停位置，新网页随决定提交 |
| 内部thread_id | 由owner及文档派生，用于定位框架状态，客户端不能指定 |
| decision | 业务库持久保存approve或reject，不能改成相反决定 |

`approval.status`区分NOT_STARTED、PENDING、APPROVED、REJECTED、BLOCKED、CREATED；这只是产品层汇总，不把框架结束等同于文件创建。已创建记录表示历史事实，重复确认才重新核对实际文件。

GET只读，服务启动不恢复执行。批准已提交但执行未完成时，用户明确重试才恢复已批准流程；明确工具失败则BLOCKED，不自动重放。业务库已CREATED时，即使框架最后checkpoint未提交，重试也先由原文件服务核对真实产物，不重新创建。

业务库、框架checkpoint和文件系统没有共同事务，不承诺跨系统“恰好一次”。例如物理文件发布后、业务状态提交前失败，可能保留文件但显示BLOCKED，用户须核对实际文件；系统不声称失败就一定没有文件。框架checkpoint丢失或损坏也可能受阻，不能单凭批准记录就无条件创建。

## 4. 接口与旧数据兼容

- POST `/v1/plans/{id}/documents`：手动准备预览并初始化审批。日常模型准备工具调用同一服务函数，仍不开放创建工具。
- GET文档与版本文档列表：附加只读approval字段。
- POST `/v1/documents/{id}/confirm`：严格confirmed=true、冻结摘要，可选interrupt_id。
- POST `/v1/documents/{id}/reject`：同样验证明确确认、摘要和当前中断；拒绝不会删除原预览或撤销已创建文件。

新页面始终发送实际中断编号。旧客户端省略中断编号时仍必须提供精确摘要和明确确认，只能决定该文档的唯一审批，不能绕过拒绝或相反决定。旧版PREVIEW可在用户显式批准/拒绝时初始化框架；旧CREATED只核对文件，不伪造新批准。

默认仍是单worker，所有决定与准备操作共用原进程串行门和应用锁；并发相反决定只有一个生效。不是分布式审批或多账号隔离。本轮未适配Open WebUI/终端的专门拒绝按钮；原生网页提供完整交互，已有确认API仍兼容。
