## 3. SDK、模型服务和 Agent 框架的区别

```text
MAGI 的任务与工具循环（自己的 Python 代码）
    ↓ 调用 SDK
Ollama Python SDK（负责请求和响应）
    ↓ 本机 HTTP
Ollama 服务（加载、运行模型）
    ↓
qwen3.5:4b（生成回复或工具调用请求）
```

- 模型：生成内容和工具调用请求。
- Ollama 服务：提供运行模型的服务接口。
- SDK：让 Python 程序方便地调用该服务。
- Agent 编排：决定上下文如何组织、工具何时执行、结果如何返回、何时停止。
- LangGraph 等框架：可以帮助组织编排；是否使用它们与模型服务选谁不是同一个层次的问题。

因此，原实验中的“直接使用 LangGraph”与“先使用 Ollama Python SDK”适合作为学习顺序的讨论，但不是两个互斥的模型接入方案。

本轮选择直接 SDK 的原因是现有环境可用、调用链短、便于逐项学习与定位问题。代价是工具循环、预算、状态和错误处理需要自己明确实现。后续出现复杂分支、持久化恢复等需求时再评估框架收益。

## 4. 已执行的最小接口实验

实验通过终端中的临时 Python 代码完成，没有新增项目实现文件，没有运行原有 `ollma_chat.py`，没有读取仓库内容给模型，也没有运行模型生成的命令。共调用本机模型三次。

### 4.1 结构化输出：一次请求

给模型提供 JSON Schema，要求返回 `status="ok"` 和整数 `value=5`，随后使用严格的 Pydantic 模型验证，并检查具体值。

观察结果：

```json
{"status": "ok", "value": 5}
```

本次客户端计时 6.16 秒；输出 token 记录为 19，结束原因为 `stop`。

这个实验检查了请求、返回、JSON 解析、字段约束与示例值，不只是检查文本“长得像 JSON”。但格式正确不代表实际业务事实正确。

### 4.2 工具往返：两次请求

只提供一个内存加法工具 `add(a, b)`，要求模型调用它计算 17 + 25。

实际过程：

1. 模型返回工具名称 `add` 和参数 `{"a": 17, "b": 25}`。
2. Python 检查只请求一次工具、名称匹配、参数恰好为两个整数，且值符合本次实验。
3. Python 执行加法，得到 42。
4. 把模型的工具请求和工具结果追加到消息中，再请求模型。
5. 模型返回 `42`，没有继续请求工具。

本次往返客户端计时 1.14 秒。只有两次固定请求，没有无限循环，没有文件或命令工具。

这里最重要的学习点是：模型提出调用请求，程序检查并真正执行工具，再将结果交回模型。模型不会因为知道函数名称就自动在电脑上执行函数。[Ollama 工具调用官方说明](https://docs.ollama.com/capabilities/tool-calling)

### 4.3 实验参数的意义

| 参数 | 本轮值 | 意义 |
| --- | --- | --- |
| `host` | `http://127.0.0.1:11434` | 连接 Windows 上的本机 Ollama 服务 |
| `timeout` | `45.0` | HTTP 客户端超时配置；不是整个 Agent 任务的总时间预算 |
| `trust_env` | `False` | HTTPX 不采用环境代理等配置，便于直接访问本机；不是清除所有 SDK 环境配置 |
| `model` | `qwen3.5:4b` | 指定已下载的模型 |
| `messages` | 用户输入，以及后续工具请求和结果 | 本次请求的显式上下文；不是自动长期记忆 |
| `stream` | `False` | 等完整响应后处理，先减少流式解析复杂度 |
| `think` | `False` | 本次短接口实验使用非思考模式，不代表最终编码策略 |
| `temperature` | `0` | 降低采样变化，不承诺绝对可重复或正确 |
| `num_predict` | 96 / 128 / 64 | 分别限制三次请求的生成 token 数量，不是字符数 |
| `num_ctx` | `2048` | 本次短实验的上下文配置，不适合直接照搬到完整仓库任务 |
| `format` | JSON Schema | 仅结构化实验使用，约束返回结构 |
| `tools` | 一个加法工具的描述 | 仅工具实验使用，告诉模型可请求什么工具及其参数 |

不要在所有请求中无差别同时加入结构化输出约束和工具参数；两者分别服务于返回业务数据和发起工具请求，应针对调用目的设计并验证。[Ollama 结构化输出官方说明](https://docs.ollama.com/capabilities/structured-outputs)

### 4.4 结论的边界

上述两个场景各执行一次，只能证明当前服务、SDK 和模型在这些小输入上的接口兼容性。计时没有做重复采样、预热控制或系统负载控制，不能作为性能基准，也不能比较 JSON 与工具调用的速度。

本轮没有验证：代码修复质量、中文复杂指令、多工具选择、恶意输入、长上下文、模型持续可靠性、9B 性能以及三人格收益。

## 5. 执行环境起步设计

```text
Windows
  MAGI 控制程序 ── 本机 HTTP ── Ollama
       │
       │ 后续由可信程序构造固定的执行请求
       ↓
WSL2 Ubuntu / Docker
  任务容器：只接触任务副本，运行指定验证
       ↓
  返回退出状态、输出、补丁或验证产物
```

模型调用留在控制程序，测试容器不需要连接模型。网络关闭只作用于任务容器，不影响 Windows 上的 Ollama 调用。

后续最小执行环境要验证：

- 目标 Python 版本和必要测试依赖预先装入镜像；依赖准备与任务执行分开。
- 仅挂载明确的任务副本，不挂载用户主目录、凭据或 Docker socket。
- 使用非 root 用户、关闭不需要的网络、限制资源及执行时间。
- 按工作负载设置只读根文件系统与必要的临时可写目录。
- 编排代码负责限定镜像、挂载和命令；不能让模型随意构造 `docker run` 参数。
- 验证取消和超时能终止任务容器中的执行。

Docker 的 `--network none` 可隔离容器网络，挂载和资源参数需要显式配置。Docker 守护进程的控制权限本身很高，因此上述方案仍需实际验证，不能仅因 Docker 已安装就宣称沙箱已完成。[Docker 网络说明](https://docs.docker.com/engine/network/drivers/none/)、[Docker 执行参数](https://docs.docker.com/engine/containers/run/)、[Docker 安全说明](https://docs.docker.com/engine/security/)

本轮没有启动容器、拉取镜像、安装依赖或修改 Docker 配置。

## 6. 接下来只做一个学习任务

目标：在你已有的 `expirements/ollma_chat.py` 中，亲自观察模型实际返回的内容。

目前脚本已经发送了模型请求，但把 `content` 手工设成“这不是JSON”，最后打印的是三条手写字典的校验结果。因此当前终端输出并不能证明真实模型结果经过了校验。

本次只替换模拟内容赋值，接上这两行，并观察输出：

```python
content = response.message.content
print(content)
```

解释：

- `response`：SDK 返回的完整响应对象，包含消息及其他元数据。
- `response.message`：本次模型回复的消息对象。
- `response.message.content`：回复正文，目前仍然是字符串。
- `content`：保存正文的局部变量；赋值不会自动解析 JSON。
- `print(content)`：把实际正文显示在终端中，便于核对。

原来的三条 `validate_choice(...)` 输出可以暂时保留，它们仍是独立的手写样例，不是模型响应验证。先明确二者区别，再继续下一次的 JSON 解析与校验学习。

在仓库根目录使用当前虚拟环境运行：

```powershell
.\.venv\Scripts\python.exe -m expirements.ollma_chat
```
