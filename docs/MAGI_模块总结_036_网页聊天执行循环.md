# 036 网页聊天执行循环

这轮改造从一个实际调试问题出发。用户让 MAGI 读资料并准备工作单，如果网页只显示处理失败，开发者需要知道程序是没连上模型、没接受工具参数，还是已经存好预览、但没拿到最后一句回答。原来模型与工具的调度由 Deep Agents 执行，项目代码通过中间件拦截各步骤。现在网页日常聊天直接执行 `ChatLoop.ask()`，可以沿同一段代码定位上述差异。三人格审议仍由原来的业务流程产生候选，工作单审批仍由原来的业务服务处理。

## 一次聊天如何执行

网页调用 `WebService.turn()`。它先按用户、聊天和消息 ID 查找原回执。同一消息及输入再次提交时直接返回记录，输入变了则拒绝。对于新消息，先将本轮登记为 `RUNNING`，再通过 `open_web_session()` 装配当前确认记忆、模型和本轮允许的工具。`open_web_session()` 复用 `open_personal_session()` 的配置，只把网页的 `ask()` 接到新循环。终端和直接调用原会话入口的脚本继续走原执行路径。

假设用户要求读取授权目录的 `note.txt`。第一条模型回复请求 `magi_read_file`，参数是 `{"path":"note.txt"}`，工具调用 ID 是 `call-0`。以下摘自 `src/magi/harness/chat_loop.py` 的 `ChatLoop.ask()`，省略了工具执行及其事件记录：

```python
stage = "tool_validation"
if (
    len(calls) > remaining_tools
    or attempt >= self.settings.max_model_calls
):
    raise RuntimeError("剩余预算不足以执行工具并继续回答")
self.validate_batch(calls)
remaining_tools -= len(calls)
```

只有预算足够，而且整批工具名、ID 和参数都通过检查，才开始执行。这样同批第一项合法、第二项参数错误时，第一项也不会提前产生副作用。参数结构来自已注册工具的 Pydantic schema，文件路径能不能读则仍由文件工具检查。预算还会保留后续一次模型请求的机会，否则程序可能执行了工具却没有机会交付回答。

`StructuredTool.invoke(call)` 接收完整的调用对象。工具返回的 `ToolMessage` 与原模型请求通过 `tool_call_id` 对应。第二次模型请求可同时看见 `call-0` 和对应结果 `NOTE-731`。循环按收到的顺序串行执行，同批调用 ID 必须唯一。最终模型返回非空文本且没有新工具请求时，循环保存本轮完整消息并返回文本。网页之后将轮次改为 `COMPLETED`。如果模型在最后一步输出截断、返回空文本或者给出无法解析的调用，本轮会失败。

## 历史与保存位置

`ChatLoop.model_input(history)` 接收旧消息和本轮暂存消息，添加系统提示词，必要时调用已有 `ConversationSummary`。摘要替换的是发送给模型的旧历史片段，原消息仍保留。之后以序列化字节数估算输入体积，并为输出和消息开销预留空间。这是容量守卫，字节数只是保守估计。摘要模型调用沿用原来的独立控制，聊天循环的请求次数统计覆盖聊天模型请求及连接重试。

完成回答时才调用 `save_messages(pending)`，因此非法工具参数或后续模型读取超时通常不会把半轮工具交互带到下一轮。为保留旧聊天和终端读取能力，本轮继续复用原 SQLite checkpoint。下面是 `src/magi/harness/runtime.py` 的实际保存方法：

```python
def save_messages(self, messages):
    """仅写消息并结束图调度，兼容旧会话和终端读取。"""
    self.agent.update_state(self.config, {"messages": messages})
    self.agent.update_state(self.config, None, as_node=END)
```

这里仍需构造旧图来读写状态，日常聊天的执行循环直接调用模型和工具。生产网页通过 `has_pending()` 和 `append_exchange()` 访问会话，三人格结果续接时以稳定消息 ID 写入，恢复时重复写入会覆盖同一组消息。现有演示注入接口仍支持旧式图适配器。

消息历史与网页轮次位于不同存储，保存消息和结束图调度也是两步。如果进程在这两个 checkpoint 写入之间中断，新循环会拒绝接着运行仍有待执行节点的旧会话。若在写完历史后、更新网页状态前中断，可能出现历史已有回答、网页轮次仍被恢复为 `INTERRUPTED` 的情况。网页重启会标记未完成轮次，已完成审议可以补写历史。这一轮没有实现聊天跨库原子提交或工具执行断点续跑。

## 失败、重试和实际业务结果

`ChatLoop.ask()` 在每次模型请求前记录尝试编号。连接建立失败时，只有本轮还没重试且模型预算还有余量，才会再发一次请求。重试留在模型步骤，已执行的工具结果继续在本轮消息里。读取响应超时可能发生在上游已收到请求之后，因此本轮直接报错。工具异常也会立即终止，事件记录工具名、调用 ID、异常类型以及最终失败阶段。日志不记录工具内容。网页对多数执行错误仍返回现有通用错误，开发者可以用网页轮次 ID 查执行事件。

把例子改成先准备工作单，再等待模型解释预览。如果预览服务先提交、模型响应后超时，网页轮次是 `FAILED`，业务库中仍有一条 `PREVIEW`。再次提交同一消息会取回原轮次及预览，既不会重跑模型，也不会重建预览。最终文件要等用户在页面确认，审批和文件服务才会执行创建。模型生成、工具预览入库、用户确认和最终文件创建分别有自己的结果。

| 标识 | 用途 |
| --- | --- |
| 网页 `message_id` | 客户端提交的一条消息，在同一用户与聊天内参与去重 |
| `web_turn_id` | 后端生成的业务轮次 ID，用于网页状态、预览来源与执行日志关联 |
| 日志 `run_id` | 一次循环的诊断 ID，和业务轮次 ID 分开 |
| `thread_id` | 当前逻辑会话及背景版本对应的历史存储位置 |
| 工具 `call_id` | 模型请求中的工具项标识，用于关联工具结果 |
| `document_id` | 工作单业务对象，从预览延续到审批和创建 |

## 验证记录

新增用例通过默认 `WebService` 装配真实工具及 SQLite 存储，只替换模型输入输出。观察到读文件结果和工具调用 ID 一致，重新打开服务后仍能载入工具消息。非法参数会使整批工具都不启动。模拟连接失败只重试模型一次，之前完成的工具只执行一次。工作单预览写入后模拟模型读取超时，重开服务并提交相同消息，仍取回唯一预览。首次编写断言时把预览状态写成 `PENDING`，测试显示实际业务状态为 `PREVIEW`，已修正断言并复测。

## 面试知识关联

**执行编排与输入校验。** 业务问题是用户一句话可能触发多次模型请求，而模型还能给出不合法的工具调用。项目自己决定继续、拒绝和结束的时机，用 Pydantic 校验参数，用模型适配层及 `StructuredTool` 处理消息协议。若被问为什么整批先检查，可以用第一项准备预览、第二项参数无效的例子说明。预检查能阻止已知非法批次，执行期第二项出错时仍无法回滚第一项已经提交的业务结果。

**幂等和失败恢复。** 业务问题是用户没收到回复时容易重复发送。后端通过消息 ID 与请求摘要返回原轮次，并通过工作单业务记录识别已产生的结果。测试覆盖预览后超时及重开服务。若被问能否保证任意崩溃下都恰好执行一次，可以指出聊天 checkpoint 与业务库各自提交，现有证据只覆盖已测试的失败位置。后续可以评估把完整消息与网页完成状态放进同一事务。

建议先读 `WebService.turn()` 的聊天分支，再读 `ChatLoop.ask()` 和四个离线用例，最后看 `HarnessSession.save_messages()`。复述时可以用三个问题自查：

1. 第一次模型返回工具请求后，代码在哪些条件下会在执行前拒绝整批？
2. 连接失败和读取响应超时为什么分别走不同分支？之前执行的工具会不会再执行？
3. 预览已入库、最后一条模型响应超时时，网页轮次、工作单记录和模型历史分别留下什么？
