# 模块031：三人格目标与证据边界、固定内容对照

日期：2026-11-02。用户完成分块与缓存复述后明确同意继续。本轮围绕已经出现的内容偏移，完善三个角色与综合共用的生成约束，完成真实前后对照及完整程序回归，不新增检索组件或模型调用阶段。

## 1. 为什么做这一轮

此前检索已能找到并保留原文，但模型仍把其他片段中的“先备份再迁移”安排进只要求解释和核对的任务，还把哈希一致说成“确认未被篡改”。这说明资料引用合法与用户目标被满足是不同层次。

本轮目标是减少这种偏移，并得到可追溯的真实内容证据。没有增加“某句话一定错误”的大量专用字段，也没有添加第二个模型裁判。程序依旧检查结构、引用和明确预算；用户仍决定是否保存正式计划；内容是否合理需要单独复核。

## 2. 实际业务链路与改动位置

当前问题/约束 + 有效记忆 + 旧计划 + 冻结资料 → 三个角色独立意见 → 综合候选 → 程序校验 → 用户确认 → 正式计划写入。

此次只在Council._generate的共享入口追加统一边界，使三角色和综合均接收相同指导。检索、分块、向量缓存、source目录、生成Schema、候选确认接口、计划数据库事务均未改动。页面操作不变；正常启动后新回合使用新版提示，历史回合保留原有意见和诊断，不会重新生成。

## 3. 核心代码：共享生成约束

文件：`src/magi/council/grounding.py`，实际交付内容：

```python
"""审议的目标与证据使用约束；提示指导不替代引用校验或用户授权。"""

POLICY_VERSION = "goal-evidence-v1"
GROUNDING_GUIDANCE = (
    "\n目标与证据边界：候选行动只服务当前question明确的目标；"
    "资料中出现某个操作不等于用户要求或授权该操作。"
    "与当前目标无关的迁移、采购、写入等建议不得因资料提及就成为计划步骤；"
    "确实必要但尚未获知的前提列为待确认事项，不先安排执行。"
    "原文引用合法不等于结论受支持，说明中的事实判断须能由所引原文支持；"
    "新增建议明确作为建议或假设，不冒充来源规定。"
    "无结果仅说明本次检索范围和预算内未匹配，不宣称整个资料库不存在相关内容。"
    "内容哈希和版本一致只支持快照一致性核对，不证明来源可信、授权修改或未遭篡改；"
    "不要将version_id与sha256直接比等，它们标识的对象不同。"
    "核对类任务的完成条件应允许记录通过、失败、差异或证据不足，"
    "不要求被核对对象必须成功才算完成核对。"
    "共识和分歧必须对应角色实际表达；角度不同不自动构成意见冲突，没冲突就写空列表。"
)

```

POLICY_VERSION标识一套生成指导，不是文档版本、计划版本、模型版本或操作回执。它允许查询某次角色响应使用的是哪套指导，不能证明响应已经遵守全部要求。

GROUNDING_GUIDANCE是系统提示的一部分：当前question决定目标，资料不能因提到某个操作就扩大授权；事实陈述应有原文支持，新增建议与假设要区分；未匹配只表达本次检索边界；哈希一致只支持内容一致性；核对允许失败/差异/证据不足；角色不同角度不自动成为分歧。

这是生成指导，不是确定性语义过滤器。CASPER在本轮无结果案例中仍违反了范围表达要求，原始输出保留。没有通过写上“不得”就宣称已经防止所有越界或幻觉。

## 4. 核心代码：如何进入实际调用

文件：`src/magi/council/service.py`，_generate入口摘录：

```python
    def _generate(self, system, payload, schema, budget, timeout, diagnostics):
        """记录用量并解析结构化响应；校验失败向上抛出，不自动修复或重试。"""
        # 三个角色和综合共用边界；这是生成指导，不是程序已证明语义正确。
        system += GROUNDING_GUIDANCE
        diagnostics["grounding_policy"] = POLICY_VERSION
        diagnostics.update(
            output_budget=budget,
            timeout_seconds=round(timeout, 3),
            snapshot_payload_chars=len(payload),
        )
        response = self.invoke(system, payload, schema, budget, timeout)
        if isinstance(response, str):
            raw = response
        else:
            raw = response.text
```

| 参数 | 业务意义与来源 | 使用及边界 |
| --- | --- | --- |
| system | Council.run为当前角色或综合构造的任务指导 | 追加共享约束，不修改用户快照 |
| payload | 已冻结快照JSON；综合时还包含真实角色意见 | 同轮角色读取同一份证据，不重新检索 |
| schema | Opinion或Synthesis业务模型 | 原有结构约束和Pydantic解析继续生效 |
| budget | 程序给定的输出token预算 | 三角色每次768，综合1536；不是用户分钟预算 |
| timeout | 原有整轮剩余时间内的单次超时 | 本轮没有放宽超时或自动重试 |
| diagnostics | 当前角色/综合的可变诊断字典 | 附grounding_policy，后续随回合结果持久化 |

_generate由run调用；self.invoke默认是真实模型适配器，也可由离线测试注入替身。程序追加指导后仍走原有invoke、消息校验和schema.model_validate_json；若有工具调用、坏结构或伪造来源，原有拒绝机制不变。返回的是解析后的意见或综合对象，不执行数据库确认保存。

新增的grounding_policy记录在每个角色diagnostics及synthesis_diagnostics中，便于对照；既有output_budget、timeout_seconds和用量记录仍保留。没有新增业务数据库迁移，没有把策略版本混进plan_id或source编号。

### 一个输入输出的具体差别

用户只问“SQLiteRestart重启时恢复什么、未确认计划是否已保存”，检索片段另外包含“先备份再迁移”。旧版真实候选安排“先备份数据库，再执行迁移或恢复操作”。新版这一次输出定位原文、记录比对结果和资料缺口，没有把迁移变成步骤。

原文“先备份再迁移”仍然存在，不是检索删除它；变化在于生成阶段是否把它当成当前用户要求。即使模型输出只读核对建议，用户仍需确认后才会保存为正式计划；本轮对照没有调用确认或执行接口。

## 5. 固定真实对照怎么做

脚本：scripts/evaluate_grounding.py。三个完全相同的冻结输入分别运行旧版和新版，每例最多3+1次调用，共上限24次。前后各一次，不自动修复或重试。真实模型为当前千问配置；没有embedding调用、检索重跑或本地模型启动。

两个案例来自历史失败：模块030的范围/哈希案例、模块028的无匹配案例；第三个是新编写的显示器购买准备情境，用户明确只整理询问问题、不选型不下单，资料却含完整采购流程。第三例是开发验收新场景，不是独立盲测，更不称为大规模独立评价。

复用旧快照是为了隔离检索波动。历史快照里的文档/版本/分块ID仍只解释该快照，不能拿来自动读取本轮磁盘上的同名文件。脚本deepcopy每份输入，避免某次调用修改共享测试数据。

baseline_council(directory)从固定旧提交69ad835提取service.py，保存到独立测试目录，用importlib加载旧Council。directory来自命令行的新data-dir，不触及用户正式数据；函数返回旧Council类型和源码SHA256。固定提交避免脚本提交后HEAD变化导致“旧版其实也是新版”。首跑初版从当时HEAD提取，已核实其源码哈希与69ad835完全一致；后续入口显式固定该提交，不改写原始证据。

参数settings来自已有magi.qianwen.toml，只使用生成接口；output是新报告路径，data-dir必须为新目录，均拒绝覆盖。每完成一个案例即保存snapshot、result和耗时。异常只记录类型，不记录平台异常正文或密钥。报告记录数据集哈希、旧实现哈希和运行工作区指纹，不根据关键词自动宣布语义通过。

首跑脚本是在结束时记录工作区指纹，期间固定旧提交这一小调整发生在脚本文件中，故脚本指纹描述结束时文件，不是严格的入口编译字节指纹；实际产品service与grounding内容未在运行中改变。后续脚本已把指纹采集移到调用前。原报告保留，不伪造为首跑已有最终采集顺序。

## 6. 真实结果：完成率与内容分开

[原始六次结果](validation/031-grounding-first.json)：全部COMPLETED，共24次真实调用，输入37382、输出4400、合计41782个已知tokens。没有核实单价，不计算金额。新共享提示会增加输入长度，不能宣称此次同时降低了成本。

| 场景 | 旧版这次结果 | 新版这次结果 | 人工复核结论 |
| --- | --- | --- | --- |
| 历史范围/哈希 | 安排备份迁移；称比对version_id与sha256确认未被篡改 | 不安排迁移；只表述快照一致性，核对条件允许记录通过/失败/差异 | 主要问题在本次收敛，但assumptions仍写“假定文件未被篡改”，不能把假设当事实 |
| 历史无结果 | 综合说明资料缺口，角色对能否给通用步骤意见不同 | 综合限定本次无匹配、允许记录证据不足 | CASPER仍写“当前资料库中无相关记录”，范围过大；不能说所有角色内容通过 |
| 新采购准备 | 两步准备，无下单，但将不同方法描述为分歧；部分角色说负担极低、完全可逆 | 两步整理问题，无选型和下单；分歧为空 | 旧版原本也没下单，不能声称新增了原本不存在的避免下单收益；新版仍有“负担极低且完全可逆”的无充分依据断言 |

新版historical_scope的revision_reason出现“不宣称资料支持结论”的笼统措辞，表达偏防御，不等于对每个事实完成了支持检查。具体哈希核对仍缺用户可直接操作的步骤。采购场景中“商家是否支持自定义接口配置”也不一定适合普通显示器询问，需要用户核对。

这些结果说明：共享指导在若干本例上改善了目标约束和证据表述，但仍会失败。固定输入不等于输出确定；对照顺序是先旧后新、每个只有一次，没有随机交叉或多次统计，模型服务自身变化也可能影响输出。不能用6/6结构完成推导语义正确率、长期可靠性或普遍改善比例。

## 8. 与后端/Agent面试知识的关联

以下是结合本轮实际代码的通用工程追问，不声称是某家公司当前真题；没有虚构面试频率或线上规模。

### 8.1 Schema通过为什么还可能回答错误

业务问题是来源ID合法但迁移建议超出目标。对应知识是结构契约与语义约束的区别：Pydantic能验证字段、类型和长度，引用白名单能确认来源存在；两者不能证明建议符合用户意图。

本项目证据是historical_scope旧版COMPLETED仍安排迁移，以及新版missing仍有范围夸大。面试回答应说明“我用确定性程序守住结构和保存边界，用固定真实评测和人工复核观察内容”，不能说“用了JSON Schema就没有幻觉”。本轮自有贡献是统一指导和可追溯对照，上游模型及结构化输出框架不是自己实现的。

可能追问：为什么不直接把不相关回答正则拦截？回答要点：任意自然语言目标难以靠穷举规则覆盖，错误规则还可能拒绝合法请求；这里没有实现通用语义证明，也没有宣称解决，重要决策继续由用户确认。未来可以评估更强内容验证，但增加调用、延迟和验证器自身错误也要测。

### 8.2 如何让LLM实验可追溯，而不是挑选好回答

业务问题是改提示后结果看起来更好，是否能归因？对应知识是控制变量、固定数据集、版本记录与可观察性。代码证据是evaluate_grounding复用同一snapshot、保存旧源码哈希、逐次保存所有结果，以及每个诊断携带POLICY_VERSION。

回答要点：固定输入减少检索干扰，但LLM仍可能非确定；本轮样本小、顺序未随机，只能报告这次观察。没有统计重复试验就不报总体改善率。POLICY_VERSION说明用过哪套指导，不代表模型权重固定或结果已经合格。

可能追问：为何不能在看到失败后重试直到通过？因为会改变评测含义并掩盖失败概率；本项目复测应使用新结果文件保留原始尝试，而不是覆盖。实际用户重试是新的操作决策，与固定评测挑结果不同。

### 8.3 数据完整性与授权为何不能混为一谈

业务问题是模型把哈希一致说成“未被篡改”，把资料提到的操作当成用户要求。对应知识分别是内容一致性、来源可信和操作授权：哈希是内容指纹，若内容和期望哈希同时被替换，仅比较二者不能确认可信来源；文档中写“可下单”也不是当前用户已经授权购买。

本项目中哈希用于快照追溯，正式写入仍由确认接口和事务完成。可信签名、外部信任链或通用权限证明属于未实现的其他能力，不能在面试中说自己已做。本轮的提示约束同样不能替代后端实际确认检查。

可能追问：模型说已保存，为什么还要看数据库回执？回答要点：生成文字是建议，提交成功是程序和数据库的事实；以前模块实现了候选内容绑定、确认和幂等回执，本轮没有重写或新增这些机制。结合现有证据讲清自己适配的部分和复用框架的部分。
