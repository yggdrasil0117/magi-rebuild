# MAGI 模块总结017：自动记忆候选与确认

日期：2026-10-30。已先补充设计，再实现一轮有界功能。

## 1. 设计依据与范围

原v0.2第8节已有“普通聊天推测出的候选先等待确认”的原则，但没有具体提取流程，自动大规模抽取仍不在当前范围。本轮先新增[设计决策003](MAGI_设计决策_003_自动记忆候选.md)，并链接进v0.3计划，然后实现有界的P1自动候选。

日常使用不必先打开记忆表单：自然表达后，页面可能出现“要记住这个信息吗？”卡片。它提供建议内容、用户原话和理由；已有同名记忆时显示旧内容及“确认替换”。用户可编辑内容、确认或忽略，手动管理仍保留。

**自动的是提出建议，不是自动写入长期记忆。** 未确认候选与有效memories分开存储，生成和忽略均不改变context_epoch。

## 2. 一条消息怎么走

```text
原聊天/审议完成 → 先显示回答
  → 原生网页独立请求一次记忆提取
  → 当前用户表达 + 有效全局记忆 → 有界模型分类
  → 原文编号回填、重复检查、同名更新识别
  → 待确认卡片
用户编辑确认 → 固定操作ID → MemoryService事务 → 有效记忆及epoch更新
用户忽略 → 标记候选已忽略，不写有效记忆
```

提取不读取助手回答、人格意见或旧计划。模型只从用户当前直接表达判断稳定偏好、背景、长期目标；临时约束、第三方引用、未确定想法应不提出。判断仍可能出错，原文真实不代表概括完整，用户确认不可省略。

原文片段由程序生成，模型只选编号，不自己抄写。按空白、大小写归一化后的名称和内容做确定性去重，同名不同值绑定旧记忆ID及版本，不静默覆盖。不同名称的语义重复、标点变化等不保证被识别；模型尽量复用已有名称，但不构成算法保证。

已忽略或已处理的相同原始候选不反复提出。如果用户之后改变主意，目前可通过手动记忆管理保存；本轮未实现忽略有效期或重新启用某条建议的专门入口。

## 3. 开销、恢复与边界

- 每条成功消息最多额外一次提取，输出最多512 tokens，读取响应配置最多20秒，无自动重试。原审议仍最多4次，整页流程最多可有4+1次，提取用量单独记录。
- 回答不等待提取完成。提取模型等待不占主生成串行门，冻结输入时才短暂获取它；同时只允许一个提取任务，忙时跳过，不无限排队。
- 当前背景下最多3条待确认候选，快照超过12000字符时跳过。原文目录本身有大小限制，不能保证长文本所有片段都可被选择。
- HTTP分阶段超时不是墙钟硬取消；返回已超过提取期限的结果不接受。失败不改写原回答，不把它标成聊天失败。
- 刷新只恢复已有候选，不重新提取；重启把进行中提取标为中断，不自动重放。
- 设置里可关闭自动提出，暂停后正常聊天不新增提取；浏览器只保存这个非敏感开关，不保存凭据或记忆内容。它不是账号级设置。

候选绑定owner、轮次、会话与epoch。确认前检查背景和旧记忆版本；第一次提交冻结用户编辑值，以候选ID生成固定写操作ID。提交后、候选状态更新前中断时，按真实操作记录恢复；重复确认不再次写入，不接受更换内容覆盖原操作。

确认一个候选会推进epoch，其他旧背景候选不再展示或允许确认，需要后续交流重新提出。这是当前保守的一致性边界，不代表已实现跨版本自动合并。

同轮同时出现计划和记忆候选时，确认记忆也会让原计划候选过期。建议先确定长期背景，再重新生成计划；本轮没有实现按影响范围细分失效。候选卡片在确认前提示这个影响。

新增数据库schema4仅增加提取记录和候选表；迁移在事务中完成，失败回滚新增结构并关闭连接，保留已有记忆、计划与聊天。旧版本程序不能直接读取更高schema，不能将回退代码当成数据库降级方案。

当前仍是单用户本机实例。候选owner隔离检查已做，但有效全局记忆和epoch尚未完成多账号隔离，不能据此声称支持多租户。

### 真实千问小批

八个固定案例、最多八次提取调用，主回答为桩，无确认、无重试。稳定偏好、背景、长期目标、同名更新四例提出候选；临时安排、文档示例、未确定想法、重复偏好四例不提出。八例分支检查符合预设，全部有效记忆保持不变。

人工复核四份候选：三份内容忠实；长期目标一例遗漏了用户的“一年”期限，需编辑补上。**8/8分支检查不等于8/8内容质量通过**，更不是普遍准确率。

八次均有用量：输入3309、输出301、合计3610 tokens；提取耗时约2.55—3.56秒，只代表这批结果，不是正常聊天耗时或未来时延承诺。基准提交与关键源码指纹保留，导出时验证指纹一致，密钥不进入报告。

记录：[真实结果](validation/017-memory-cloud.json)、[人工复核](validation/017-memory-review.json)。

### 真实浏览器

Playwright CLI控制真实Edge，真实FastAPI与SQLite，主回答和提取器均为桩，不调用模型：

1. 预置一条“回答尽量详细”的记忆。自然聊天后自动出现更新候选，展示原值与原话；旧记忆仍是v1、epoch1。
2. 忽略第一条后没有写入；第二条建议保持待确认。
3. 刷新并重新连接后恢复待确认卡片，提取记录仍只有2次。
4. 用户将建议改为“解释技术问题时先给具体例子，再讲原理”，确认后更新同一记忆为v2、epoch2。实际保存的是编辑值。
5. 暂停自动建议后第三条聊天正常回复，提取记录仍为2；开关关闭后再次刷新仍关闭，服务凭据为空。

最终5次业务操作中4次为演示预置数据，仅1次为用户确认更新。截图已查看，测试API和浏览器均已关闭。新增记忆确认由离线集成覆盖；浏览器主要覆盖更新、忽略、恢复与暂停，未进行移动端或浏览器进程崩溃专项。

## 5. 阅读顺序

先看 `personal/extraction.py`：模型只负责分类和提出。再看 `personal/suggestions.py` 的start、finish、confirm：分清提取尝试、候选及有效记忆。最后看网页的异步触发和确认按钮。

| 标识 | 职责 |
| --- | --- |
| turn_id | 关联产生候选的用户消息与主回答，同轮不重复提取 |
| suggestion_id | 一条待确认记忆建议，不是有效记忆ID |
| target_id / memory_id | 同名更新时指向已有记忆，新增确认后才产生新的memory_id |
| 固定操作ID | 确认的幂等依据，避免中断或重试重复写入 |
| context_epoch | 只在有效记忆实际变更后推进，提出和忽略不推进 |

本轮延续既有确认与幂等机制，不为新增功能凑question.md条目。完成后等待用户阅读复述；下一步按真实体验决定，不提前开放无确认记忆写入或大规模后台处理。
