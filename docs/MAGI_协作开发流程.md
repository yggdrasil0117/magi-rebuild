# MAGI 协作开发流程：设计、执行与学习

日期：2026-10-29。状态：用户已确认的后续协作方式。

## 1. 分工

用户要求：先由当前模型设计开发文档，之后切换到执行模型（用户举例为 5.6sol、6.1sol）进行开发，继续边学习边开发。这里记录角色分工，不预设这些模型的价格、速度或质量，也不代表已经自动切换模型。

| 角色 | 交付 | 边界 |
| --- | --- | --- |
| 设计模型 | 可实施任务书，明确产品行为、数据、接口、失败路径和验收 | 不在一次设计讨论中顺手实现下一批业务代码 |
| 执行模型 | 按任务书提交完整功能、解释、测试及模块总结 | 保留当前代码基础，不自行扩大范围或改写产品定位 |
| 用户 | 运行体验、阅读核心流程、完成小改动、反馈理解和使用问题 | 无需先独立写出全部实现才能推进 |
| Review 模型 | 对照任务书审查代码和运行证据，指出真实缺口 | 不把解释流畅、测试数量或一次模型回答当作完整产品验收 |

用户切换模型并发出执行请求后，任务书作为共同开发依据。范围内的常规实现选择由执行者完成，不逐字段、逐行请求确认。需要改变产品行为或核心约束时，先说明影响并记录决策；不把普通实现细节升级为新的审批流程。

## 2. 设计任务书必须包含什么

1. 当前代码与已验证能力、任务目标、范围及暂不实现的内容。
2. 一段可以实际走通的用户故事，标明对应设计与验收编号。
3. 要新增或修改的文件，以及已有模块如何复用。
4. 数据对象、必要字段、不变量、关键接口与输入输出。
5. 正常流程、异常流程、事务、版本、幂等与恢复边界。
6. 模型负责判断的部分、程序必须确定性校验的部分。
7. 完整功能单元的实施顺序，避免逐行拆成大量轮次。
8. 离线测试、真实模型试验的具体通过条件，以及它们各自不能证明什么。
9. 关键知识点、代码阅读顺序、一个不阻塞交付的小练习。
10. 完成后的总结文件、检查结果、剩余问题与交接说明。

任务书要让未参与此前聊天的执行模型读完即可工作。明确仍未决定的事项，给出保守默认方案，不依赖它猜测聊天记录。

## 3. 执行与学习节奏

当前以整个可演示 MVP 为交付目标，按可运行的完整功能阶段连续推进：先解释本阶段解决什么问题和主要调用关系，再完成实现；说明关键参数、数据流与失败处理；执行必要检查，并提供用户运行命令。阶段完成后安排一个可选小改动或阅读问题，不要求用户先交练习才能继续开发，不逐字段停下来确认。

代码解释集中在本轮的新知识，不重复介绍已经掌握的每个基础语法。不要求用户逐行照抄，也不一次丢下大量代码让用户自行理解。

实现中遇到失败，由执行模型定位和处理；总结写清失败原因和修复依据。如果受外部条件限制，精确记录已完成与待验证部分，不冒称通过。模型服务切换和框架接入也遵守这一点。

## 4. Review 与留痕

每个模块生成编号总结，对照当前设计和任务书记录：实际改动、复用点、测试命令及范围、真实模型证据、限制、学习重点和下一步。测试结果注明时间及环境。

Review 优先检查业务不变量和用户行为：是否恢复了正确会话、撤销的信息是否还会回流、重复操作是否产生重复结果、失败是否被误报成功。新增库或复杂抽象必须有实际用途。

设计文档描述目标；任务书约束本轮交付；模块总结记录事实。三者不互相冒充。文档中的历史“下一步”不自动变成当前开发命令。
