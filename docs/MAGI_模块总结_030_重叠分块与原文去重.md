# 模块030：重叠分块、原文去重与旧缓存隔离

日期：2026-11-01。用户完成上一轮复述并同意推进。本轮只补齐已有检索的完整原文边界和候选重复问题，不引入新模型、融合重排或新的知识库框架，也不根据少量样本调整0.45阈值。

## 1. 业务作用与完整链路

原文每160字硬切，跨切口的词可能两边都不完整。例如SQLiteRestart从第157个字符开始，旧第一块只有前缀，第二块只有后缀。关键词不能命中完整标识，向量也可能先找到含普通SQLite的其他片段。另一方面，同一文档重复多次相同提示，会挤占最多5条返回位置。

本轮改为160字窗口、32字重叠，保持原始行号与行内字符位置。完成检索排序后，抑制同一文档版本中已经被选中原文完整覆盖的重复片段，再取前5条。真实片段仍直接来自文件，不让模型拼接或补写。

读取授权文件 → 文档版本 → 重叠分块 → 关键词或向量检索 → 排序 → 原文去重 → 最多5条证据 → 冻结给三人格 → 引用校验 → 用户确认后保存计划。界面和正式计划确认接口没有变化；普通日常search_files工具仍维持原来的字面搜索行为。

正常使用无需新操作。第一次运行新策略时会重新生成对应分块向量，因此可能产生新的embedding调用与缓存记录；旧计划依据和旧索引不会被改写或删除。

## 2. 核心代码：重叠窗口

文件：`src/magi/retrieval.py`。当前策略名为`CHUNK_POLICY = "line160-overlap32-v2"`。

```python
def chunks(text):
    """每行160字窗口、相邻重叠32字；原文及位置不改写，不产生已被覆盖的短尾块。"""
    for number, line in enumerate(text.splitlines(), 1):
        for offset in range(0, len(line), 128):
            quote = line[offset : offset + 160]
            if quote.strip():
                yield number, offset, quote
            if offset + 160 >= len(line):
                break
```

`text`来自scan_documents实际读取并解码的授权文本。返回生成器，每项为`(number, offset, quote)`：number从1开始表示原文行号；offset从0开始表示该行字符位置；quote是原行的实际切片，长度最多160。这里按Python字符计数，不是UTF-8字节位置或模型token位置。

步长128等于窗口160减去重叠32。第一块覆盖0—159，第二块覆盖128—287，因此128—159同时存在于两块。固定示例中SQLiteRestart从offset156开始，能完整进入第二块。

末尾`if offset + 160 >= len(line): break`避免第一块已经覆盖全行之后再生成重复短尾块；恰好160字的行只产生一块。空白块不作为证据，但原文中非空片段不strip改写。保留原始位置便于核对。

这不是句子理解：超过32字的长语义单元仍可能跨边界；不跨行合并，因此一句话被原文件拆成多行时仍可能缺上下文。没有声称消除了所有分块歧义。采用固定窗口是当前有界纯文本场景的小实现，没有新造通用文本处理框架。

## 3. 为什么分块策略要进入ID

本轮新的分块身份计算为：

```python
chunk_id = digest(f"{CHUNK_POLICY}:{version_id}:{line}:{offset}")
```

各字段来源：CHUNK_POLICY是程序策略版本；version_id绑定文档身份与实际字节摘要；line和offset来自chunks。digest返回SHA256字符串，不是相似度。

同一份文件没有修改时，document_id和version_id不变；策略改变后chunk_id改变。向量缓存仍以`provider + chunk_id`寻址，因此新策略不会误用旧策略缓存。缓存命中判断不是简单比对路径或第几块。

旧chunks和embeddings表记录保留，不对历史web_turn重新分块、不重写source编号，也不覆盖已保存计划原文。新检索只遍历本轮构造的候选，历史缓存不会因为仍在表内就成为当前材料。新策略可能增加缓存体积；当前依旧没有历史缓存容量治理，不能将此称为零成本升级。

## 4. 核心代码：排序后选择不重复原文

```python
def distinct_matches(candidates, limit=5):
    """按已有排名保留同版本内不重复/不包含的原文，跨文档相同文字仍各保留来源。

    candidates已按检索分数排序。返回有界候选及去重计数；不合并原文或生成新证据。
    """
    unique = []
    removed = 0
    for item in candidates:
        if any(
            item["version_id"] == chosen["version_id"]
            and item["quote"] in chosen["quote"]
            for chosen in unique
        ):
            removed += 1
        else:
            unique.append(item)
            if len(unique) > limit:
                return unique[:limit], removed, True
    return unique, removed, False
```

参数candidates是已按当前检索方法排好序的候选；limit是程序固定的返回预算，默认5，用户或模型不通过工具修改它。返回值为`(selected, removed, truncated)`：selected是最终原文候选；removed是实际检查过程中已移除的重复数；truncated表示已经发现超过返回上限的不同候选。

检查只在同一version_id内进行；当前版本ID已经绑定文档，因此不同文档的相同文字仍保留各自来源。若候选quote已经完整包含于先选原文，则该候选不再占名额。反方向不能直接抑制：先选中短句“SQLite”，后面“SQLite还需要备份”有新增信息，应保留。此处只判断原文包含关系，不判断两个不同句子语义等价。

去重不会拼接片段或制造新的引用ID，选中的仍是原候选。发现第6条不同候选后即可确认只能返回前5条，立即停止，避免对整个大候选集做平方级两两比较。removed只表示停止前观察到的重复数，不冒充全库重复总数。

例如一个文档重复8次“SQLite repeated”，随后还有“SQLite additional”，另一个文档也写了“SQLite repeated”：旧的先取前5条会被重复句占满；现在返回同文档重复句一次、补充句一次、另一文档的独立来源一次，共3条。实际测试验证去掉7条重复，不将这种有意去重标记为返回预算截断。

## 5. 和向量预算、引用、保存的关系

向量阶段仍最多扫描候选的前128块；每批32条、查询最多2000字、阈值0.45均不变。重叠可能增加原文块数，使128块预算更早耗尽，这属于权衡；有budget截断时仍标记complete=False。这里没有改成无限上传或全库语义召回。

去重发生在排序后，不改变向量模型、原始余弦分数或关键词计分。向量失败仍明确退回关键词，也会执行同样的返回去重。去重不代表坏语义被过滤：上一轮的休息资料误召回属于相关性问题，不因这轮分块修改就自动解决。

证据仍在模型调用前冻结。检索文档/版本/分块及向量缓存可以先写入；三人格输出的是候选建议，只有用户确认后才写正式计划。真实评测本轮只运行Council，不调用确认接口，没有保存正式计划或执行任何迁移操作。

人工复核发现两个实际问题，保留不掩盖：

1. 其他SQLite提示干扰了回答，综合给出“先备份再迁移”，而用户没有要求迁移。说明候选混入其他相关词片段仍可能引起建议范围扩大。
2. 模型建议比对version_id和sha256“确认未被篡改”，这种表述过强。哈希一致只能帮助核对读取内容，不能独立证明来源可信、修改经过授权或从未被篡改；两个ID本身也不是同一对象，不应直接互相比等。

因此本轮程序边界与真实引用链路通过，但内容不能宣称全面正确。没有为了让人工复核看起来通过而修改原始意见或自动重新生成。核心目标是补齐证据，而不是证明三人格建议必然正确。
