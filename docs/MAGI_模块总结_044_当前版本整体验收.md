# 模块044 当前版本整体验收

## 这轮验收的版本和目标

以本地提交 `960aae8` 为产品基线，重新跑一个完整任务。旧版本有过真实验收，模块041到043也分别验证了后台任务、外部写入边界和备份。本轮让这些能力中的主链在同一份隔离数据上串起来，确认基础设施改造后，用户仍可以从对话走到计划、执行反馈和恢复。

验收任务是「在 60 分钟内核对登录接口」。资料是合成的核对指南，包含先查日志、测试账号缺失时的范围，以及最终记录缺口。验收过程中没有真的访问登录系统，也没有把工作单创建视为完成任务。

## 一条任务怎样经过当前实现

第一轮通过 `POST /v1/tasks` 提交普通聊天。执行器领取后，真实千问调用 `magi_read_file` 读取合成指南。后台任务关联一条已完成日常轮次，没有产生计划候选。第二轮进入三人格，检查它的快照确实包含这条日常聊天。两轮审议都通过真实 BGE-M3 检索，第二轮命中三个原文块的向量缓存。每轮三个角色和一次综合均完成。

执行到候选时，库里仍没有计划。验收脚本模拟用户，先读取候选哈希，再走与页面相同的 HTTP 确认接口。首次保存得到计划 v1，重发相同确认得到同一个计划的重复回执。工作单单独走预览和批准。预览阶段磁盘没有文件，批准后文件与预览逐字节相同。

然后用户自报「已整理日志，没有测试账号，只剩 30 分钟」。脚本确认阻塞记录，重发原请求仍返回原事件，使用过期 revision 的新请求被拒绝。第三轮的审议快照读到旧计划及这条执行记录，生成修订建议。确认后得到 v2。v1 仍保留阻塞，v2 的执行状态是未开始。旧工作单继续引用 v1。

本轮扩展了 `scripts/accept_current_mvp.py`，原有模式继续可用，`--extended` 才启用后台聊天和工作单。下面是核对日常轮次是否真正读取资料的代码摘录：

```python
tools = [
    event["name"]
    for event in events
    if event.get("web_turn_id") == daily["id"]
    and event["type"] == "tool_started"
]
report["daily_tools"] = tools
check("daily_selected_read_tool", "magi_read_file" in tools)
check("daily_did_not_create_candidate", daily["proposal_id"] is None)
```

`daily` 是任务回执关联的实际聊天轮次，`web_turn_id` 用来把记录过滤到本轮，避免拿同一文件中其他任务的工具记录充数。工具名证实这轮请求了读取工具。事件审计确认工具成功，原始报告保存了完整回复，内容另作人工复核。[事件与浏览器审计](validation/044-browser-audit.json)

## 进程重启和备份还原

保存后改写源资料，并停止原服务进程。重新启动实际进程后，两个计划版本的 HTTP 响应与原记录相同。执行状态仍按版本分开，原执行请求返回原事件 ID，原审议中的冻结资料仍与改写前相同。

随后再次停服，使用模块043的备份接口创建归档，并还原到新目录。对照源库和还原库，九张业务相关表逐行相同。源库和还原库都只有一个计划、两个版本、一条执行记录和一份工作单。归档包含业务库、审批 checkpoint 和工作单，文件逐字节相同。验收没有旧会话 checkpoint 或摘要文件，因此本次归档没有这两项，另见模块043的覆盖。[还原审计](validation/044-restore-audit.json)

## 内容人工复核

初版的时间安排是 5、20、25、10 分钟，合计 60 分钟。复现被写成有账号才尝试的条件分支。修订版将范围收缩为 20 分钟整理日志和问题、10 分钟记录结果或缺口。它去掉了复现，没有声称已定位根因。引用来自冻结资料和本轮用户输入。

三个人格的建议仍明显相似，单例不足以证明多角色带来额外价值。修订稿仍安排重新整理日志，没有充分利用反馈里「已经整理日志」的进展。它把日志访问权限写为假设，执行前仍需核实。这些是 Agent 内容质量的缺口，程序通过与真实保存都不能替代人工核对。

本轮真实生成通过 HTTP 发起，合成计划与工作单由脚本显式确认。浏览器用于还原后的读回核对。MCP 联网、真实 GitHub 写入、多用户部署、全新机器安装和长期负载没有在这个样本中重验。结论适用于当前本机单用户版和这条主链。

## 学习与复述

- **验收分层。** 怎样证明选择了工具？看与轮次绑定的事件与实际结果。怎样证明计划保存？查业务库和回执。怎样判断建议是否合理？核对用户反馈、时间、证据和完成条件。这三类证据可以分别失败。
- **状态恢复。** 同一个任务里，网页轮次完成、计划 v1 已保存、工作单已创建、用户执行已阻塞分别写在不同对象里。问到 v2 状态时，程序按计划 ID 和版本查执行记录，不能从 v1 或工作单推断。
- **重放与备份。** 重启后以同一请求 ID 找回旧事件，验证了持久回执。还原到新目录后比较独立的数据库行和文件字节，验证了快照是否携带完整业务数据。这两种试验的故障边界不同。

建议先读原始报告中的第一轮工具记录，再看第二、三轮候选与还原审计。可以复述：**为什么「已保存计划」「已创建工作单」与「用户已完成任务」必须是三个独立事实？**
