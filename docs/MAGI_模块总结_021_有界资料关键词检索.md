# 模块021：有界资料关键词检索

日期：2026-10-31。先补充[设计决策006](MAGI_设计决策_006_有界资料关键词检索.md)，再实现一轮资料检索能力，依据v0.2第10节的“先有界文件与关键词搜索”。

## 1. 业务作用与使用方式

此前助手只有列目录、读取已知文件，找资料时需要逐个定位。本轮新增`magi_search_files`，在授权资料目录内找关键词，返回相对路径、行号、实际原文及文件快照摘要，助手可据此回答并按需继续读取。

重启服务后，在日常模式可以说：“请在授权资料中搜索关键词‘工作单’，给出来源文件、行号，并说明搜索范围是否完整。”配置仍使用TOML的`[tools].root`；当前千问配置为仓库`docs`目录，只搜索明确授权的资料，不扫描整台电脑。

只支持`.md/.txt/.rst`的UTF-8文本，按**区分大小写的字面子串**匹配，例如`SQLite`和`sqlite`不同，`.*`也只当普通字符。不是互联网搜索、语义检索、向量RAG或MCP；不做上传解析平台或另一套Yggdrasil。

## 2. 请求经过哪些模块

用户请求 → 现有日常Harness → 模型提出`magi_search_files(query,path)` → 严格参数与工具白名单 → `agent/search.py`只读扫描 → 结构化工具结果 → 模型组织答案 → 原网页显示并保存聊天历史。

搜索工具与原来的列目录、读取文件一起注册，普通Harness和日常Web会话均可使用；三人格本轮没有新检索阶段，也不自动把日常检索摘要变成已登记的独立证据。无需新HTTP路由或页面表单。

核心函数`search_files`的根目录来自配置。模型只能选关键词和相对目录，不能修改预算、传新根目录或确认写入。所有实际文件检查仍由程序完成。工具不修改资料、正式计划、有效记忆或背景版本，但对话与工具结果会进入既有checkpoint；“只读工具”不等于整个聊天过程完全不落盘。

## 3. 返回内容与边界

| 字段 | 含义 |
| --- | --- |
| query / path | 本次字面词与授权根目录下的检索子目录 |
| matches[].path / line | 来源相对文件名与从1开始的文本行号，不是新的memory_id或plan_id |
| quote / quote_truncated | 实际行片段及是否截断；长行围绕命中位置截取，最多240字符 |
| sha256 | 本次实际读取文件字节的摘要，不是永久文档ID、业务版本号或权威性证明 |
| complete / incomplete_reasons | 在声明的类型和排除策略范围内，是否因预算或读取失败造成不完整 |
| skipped / 统计 | 排除、过大、非UTF-8、不可读等计数，以及观察条目、检查文件、实际读取字节 |

固定上限：**200个目录条目、40个候选文本文件、262144读取字节、单文件32768字节、8个命中片段**。所有预算由程序固定。目录枚举只作有限收集，有限集合内排序；大目录截断后的子集不保证全局排序或相关性排名。命中8条即保守停止，不继续扫描来证明是否恰好只有8条。

目录递归但不跟随符号链接或Windows目录联接；显式子目录也检查。排除点号开头的命名及node_modules、__pycache__，不按Windows资源管理器的“隐藏属性”判断。文件类型排除、隐藏命名和链接属于声明范围之外；大小、编码、权限失败属于范围内没读完，会导致complete=false。

无结果仅表示本次范围和预算内没找到该字面词，不能推导不存在相关含义。complete=true也只限本次子目录、支持类型和排除策略，不是全电脑、全部格式或事实核验完成。真实模型首例使用了“覆盖完整”的简略说法，实际含义仍受此范围限制。

文件摘要帮助对照本次快照；文件以后修改要重新检索，不能继续把旧摘要当当前状态。现有checkpoint仍可能含旧工具结果，本轮没有实现文件变化后自动清理历史、引用强制校验、文档新旧排序或语义重排。工具的路径/原文可核对，不等于模型每个结论都已被程序证明。

不增加数据库表、索引、嵌入模型或有效记忆；业务schema仍为6。保留用户现有三人格模块未提交改动和无关文件。
