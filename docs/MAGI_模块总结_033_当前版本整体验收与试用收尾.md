# 模块033：当前版本整体验收与试用收尾

日期：2026-11-02。本轮是完整验收轮，不新增任务平台或检索平台。执行结果与逐次失败记录见第六节；本轮结束后等待用户阅读、复述及明确授权，再决定下一轮。

## 一、为什么现在收尾

MAGI已经可以独立完成日常交流、三人格权衡、确认保存、执行记录和反馈修订。模块032补齐了“计划保存以后怎么办”的产品缺口。此时继续叠加功能，容易让使用入口和验证事实落后于代码。因此本轮选择把独立RAG与执行反馈放在同一条真实HTTP链路中核对，并整理当前试用方法。

此前分别验证过真实向量、真实生成、浏览器和重启，并不等于这些能力已经在本轮当前代码中一起运行。本轮新增`scripts/accept_current_mvp.py`，调用真实API子进程，使用千问、硅基流动BGE-M3和SQLite，不注入模型替身。现有`serve_mvp_acceptance.py`增加`--docs-root`，使验收只读取脚本生成的合成资料。验收进一步发现并修复了“全新会话先审议后无法继续修订”的真实checkpoint续接问题；正式启动、保存确认和版本检查不变。

融合检索、重排、误召回、无答案措辞和语义支持仍有缺口。本轮不声称解决这些质量问题，也不把它们全部当成个人MVP无法试用的前置条件。已有核心可用，下一步应由真实使用中发生的问题决定，而不是无限扩建框架。

## 二、用一件事理解整条链路

贯穿案例是“我只有60分钟，要核对一个登录接口问题”。授权资料写明：先看错误日志，再用测试账号复现；没有账号时整理日志和待验证问题，不声称已经定位根因。这里的资料是合成测试文本，不是用户真实的系统日志，也不包含生产账号。

在正常页面中，用户开启三人格并发送目标。后端检索资料，冻结本轮引用原文，三个角色独立读取同一份依据，综合生成候选。此时页面可以显示候选，但正式计划列表仍应为空。本轮脚本从HTTP接口读取列表，专门核对这一点，避免把生成成功误当成保存成功。

用户阅读候选后点击确认，后端才把确定的标题、正文、来源和操作回执写入业务库，形成计划v1。本轮验收脚本仅模拟对它自己创建的合成候选点击确认，不允许模型决定对用户真实计划的批准。随后重复发送相同确认，预期返回同一计划的既有回执。

接着用户报告：“已整理日志，但没有测试账号；只剩30分钟。”这次操作追加一条执行记录，计划正文仍然是v1，执行记录序号从0变为1。原请求重复发送，应返回同一事件；换成新请求编号但继续使用旧序号0，应返回409。两个试验分别检查“同一次操作再发”和“基于旧状态的新操作”，不能互相替代。

用户随后发起反馈修订。后端读取v1及近期执行记录，冻结成模型输入；三人格提出30分钟的新候选，确认后才产生v2。v1的阻塞记录留在v1，v2没有记录时显示未开始。最后脚本改写源资料、停止自己启动的API进程，再启动一个新进程连接同一数据目录。旧版正文、新版正文、旧版阻塞记录和原轮资料快照应恢复，且原执行请求仍可返回原事件。

本轮通过HTTP模拟上述操作，不操作浏览器。页面按钮、浏览器回执丢失和布局证据来自模块032，按历史时点保留。本轮“收到成功后再次发送同请求”也不是实际网络丢包试验。

```text
页面行为对应的HTTP请求
  → FastAPI身份与字段检查
  → WebService组织检索和三人格、冻结候选
  → 用户确认接口调用PlanService保存计划版本
  → execution接口调用PlanExecutions追加用户自报
  → 反馈请求冻结旧计划和近期记录，生成修订候选
  → 再次确认保存v2
  → 实际API子进程停止、重启、查询并比较结果
```

## 三、各编号分别指什么

| 编号 | 对象、来源和生命周期 |
| --- | --- |
| chat_id | 一段连续对话，脚本固定为acceptance；不是计划身份 |
| message_id、reply_message_id | 本轮用户消息与助手回复，脚本生成u1/a1、u2/a2；重复消息需要保留原编号 |
| parent_reply_message_id | 本次消息接在哪条回复之后；第二次请求传a1，证明按顺序续接，不表示计划版本 |
| turn id | 后端生成的一轮处理身份，保存本轮结果与冻结依据，用于恢复和追溯 |
| proposal_id、payload_hash | 一份候选及其确定内容摘要；用户确认绑定这份内容，摘要不证明建议正确 |
| plan_id、计划version | 正式计划及不可变版本，确认v1、修订确认v2，旧版不被覆盖 |
| request_id | 执行提交的客户端编号，本例blocked-1；重发必须保持内容和编号一致 |
| event_id、execution revision | 已追加执行事件的后端身份与此计划版本内的记录序号；一份v1可以有多条执行事件 |
| document_id、version_id、chunk_id | 资料、资料内容版本与原文块的身份；属于检索域，不等于计划version |
| PID | 操作系统中的服务进程编号；本轮记录两个不同PID，配合停止等待和重新启动证明实际进程更替 |

## 四、验收入口为什么这样写

### 4.1 数据隔离和失败保留

`accept_current_mvp.run(root, output)`由命令行调用。root是本次专用数据目录，output是本次JSON报告路径，均要求事先不存在；两种API凭据只从环境获取。返回布尔值，主入口据此设置进程退出码：通过为0，失败为1。

下面是实际代码中的前置条件。阅读重点是：重新运行不能悄悄覆盖上一次失败，也不能把自己的业务库当作验收库。

```python
    if root.exists() or output.exists():
        raise ValueError("验收数据目录和报告必须是新路径")
    if not all(os.getenv(k) for k in ("DASHSCOPE_API_KEY", "SILICONFLOW_API_KEY")):
        raise ValueError("需要通过环境提供两种云端凭据")
```

脚本先建合成资料，再启动服务。`start()`负责启动自己拥有的子进程，传入新数据目录和资料目录，随机生成本机服务凭据。它返回Popen对象，只轮询`/health`，不会用“检查就绪”为由重复调用生成接口。启动失败时终止自己的子进程并抛错；主流程finally同样清理自己的服务，不结束其他MAGI或其他应用进程。

为了避免凭据进入命令行和报告，凭据通过子进程环境传入；报告不记录环境、认证头或异常正文。子进程标准输出被关闭，意味着启动失败时只留下有限诊断，当前需要手工使用同一入口排查，尚无专门的脱敏启动日志收集器。

### 4.2 一次HTTP尝试先登记，再保存观察结果

`run`内部的`call(method, path, body=None, expected=200)`被所有步骤复用。method/path来自固定验收流程，body是合成请求；返回实际JSON响应。它不自动重发，HTTP状态不符就终止。

```python
                attempt = {"method": method, "path": path, "request": body}
                report["attempts"].append(attempt)
                save()
                response = client.request(method, path, json=body)
                attempt.update(status=response.status_code, response=response.json())
                save()
                if response.status_code != expected:
                    raise AssertionError(f"HTTP状态不符：{response.status_code}")
                return attempt["response"]
```

先登记尝试，再发请求：如果等待响应期间出错，报告中仍能看出停在哪个请求；收到响应后立即保存，后续失败不抹去已有事实。这个JSON是验收记录，不是业务事务日志。文件写入也没有实现原子替换或断电恢复，因此它不能替代SQLite中的计划与操作回执。

`check(name, condition)`记录布尔断言，失败时抛AssertionError，外层只记异常类型及FAILED。模型返回HTTP200但业务状态FAILED时，`generation_1`仍会失败；不能仅以200判断模型已经完成。

### 4.3 确认模拟绑定具体候选

`turn(number, text, **extra)`由主流程调用两次，接收固定案例问题、时间预算，以及第二轮的目标计划和预期版本，返回真实轮次结果。它传入上一回复身份来维持顺序，并要求业务状态COMPLETED且存在候选。

`confirm(turn)`在每次生成成功后调用，先读取这条回复绑定的候选，再构造确认参数。下面是实际核心片段：

```python
                body = dict(
                    chat_id="acceptance",
                    reply_message_id=turn["reply"],
                    payload_hash=proposal["payload_hash"],
                )
                return call("POST", path + "/confirm", body), (path + "/confirm", body)
```

返回值有两部分：第一部分是保存回执，第二部分是原路径和原参数，供同请求重放试验使用。它没有直接INSERT计划表。生产中，实际写入发生在WebService.confirm调用PlanService.create/update的事务中，验收沿用同一路径。确认时仍检查候选身份、摘要、背景和版本；未保存修订所依据执行记录变化时仍拒绝，已成功保存的请求仍可恢复原事实。相关拒绝边界由现有回归覆盖，本轮没有逐条再次做云端故障注入。

### 4.4 实际进程更替后比较持久结果

`run`在修订确认后停止并等待旧进程退出，再调用`start()`。以下是实际核心代码：

```python
            process.terminate()
            process.wait(timeout=15)
            process = start()
            check("old_plan_restored", call("GET", path + "?version=1") == old)
            check("new_plan_restored", call("GET", path + "?version=2") == new)
```

这里比较完整API对象，不仅比较“有一个标题”。随后比较v1执行记录序号、v2未开始状态、本轮原资料快照和执行事件重放。即使源文件已改写，读取原轮结果也应保留旧原文。它证明本例在API进程终止后能够从同一目录恢复；没有模拟操作系统断电、磁盘损坏或跨设备还原，也不证明所有中断时刻都能恢复。

### 4.5 本轮实质修复：写入已完成历史，不应留下待执行推理

第三次真实试验中，第一次审议已完成、v1也已保存，后续反馈却被INTERRUPTED_CONTEXT拒绝。这个案例没有先做日常聊天，而是从全新会话直接审议。WebService._sync把审议问答写入harness聊天checkpoint时，调用LangGraph.update_state。对新thread，框架可能把这次更新按输入节点处理，安排后继节点。结果是业务上已经完成，图状态的next却非空，后续请求按“有未完成推理”拒绝。

业务状态与框架调度状态不是同一个对象。这里不能删除下一轮的中断检查，也不能通过再调用模型把多余节点跑完；前者会放过真正未完成的推理，后者会增加非用户请求的生成。修复明确表达“这是已完成审议的历史注入”，写入稳定ID的两条消息后，通过框架已有END更新结束本次调度。

`src/magi/web/service.py`的`WebService._sync`由审议完成后及recover中的待同步修复调用；参数turn来自已持久化的轮次。它没有业务返回值，成功后更新synced标记，异常交给上层保留未同步状态。下面两个片段均摘自实际函数，中间省略了消息对象构造。

```python
        binding = self.context.resolve_binding(self.logical_id(turn["chat"]))
        # Do not resurrect a completed old-epoch result in the new context.
        if binding.epoch == turn["epoch"]:
```

先比较背景版本。用户已经修改背景时，不把旧审议重新写回新的有效聊天。通过后，问答消息分别使用`turn['id'] + '-user'`与`turn['id'] + '-assistant'`作为固定身份，框架消息合并器据此替换同消息，恢复重写不会追加重复历史。

```python
                session.agent.update_state(session.config, None, as_node=END)
        with self.store.transaction() as db:
            db.execute("UPDATE web_turns SET synced=1 WHERE id=?", (turn["id"],))
```

END来自LangGraph成熟组件，不是自造图执行器。本机安装源码`langgraph/pregel/main.py`明确支持values为None且as_node为END时清理当前待调度任务。自有代码的贡献是选对业务调用位置：仅在已完成审议写回历史后执行，普通聊天或任意未完成任务不走这个清理入口。

两次checkpoint更新和业务库标记不在同一事务里，因此不能宣称跨库原子提交。顺序保证是先写消息、再结束调度、最后标记synced。第一步后失败时，业务库仍是已完成但未同步；recover会用相同消息ID重写，再结束调度，最后标记成功。真实图测试专门注入“消息已写、END前失败”，观察next从非空恢复为空、消息仍为两条、三人格调用仍为原来的4次、日常模型0次。它检验的是恢复协议，不是把两套SQLite包装成一个分布式事务。

修复适用于后续审议同步和synced=0的恢复。升级前已经标记synced=1、却残留待执行节点的历史会话，本轮不批量清理：同样的next也可能来自真正中断的日常推理，不能仅凭非空就删除。遇到旧会话仍提示未完成时，可在设置中换一个新会话名并加载历史，再从“我的计划”选择原计划提交反馈；已保存计划无需重建。此类旧会话的自动判别和修复尚未实现，本轮也未在用户正式库执行任何清理。

## 五、复用组件与自有工作的分界

HTTP通信、连接超时和序列化由httpx负责；服务由现有FastAPI与uvicorn运行；SQLite负责事务和持久存储；千问负责真实语言生成，BGE-M3负责文本向量。LangGraph及现有harness继续承担其原有checkpoint和Agent能力，本轮不重写这些组件。

本轮自有实现是固定业务验收的编排、合成数据隔离、独立子进程管理、逐步留证和跨进程结果比较，以及完成审议写回checkpoint的调度修复。产品中的候选绑定、计划版本、幂等、执行记录隔离和冻结证据来自之前模块；不能把复用或本轮重新验证写成新增实现。

## 七、面试知识关联

### 7.1 为什么单元测试之外还要做真实链路

本轮业务问题是“各模块各自通过，但一起运行是否有遗漏”。对应基础知识是测试层次与外部依赖边界。项目证据是429项回归之外，真实HTTP链路暴露了临时凭据读取错误和续接参数遗漏；后者在脚本模型的业务测试中不会自动出现，因为调用方构造不同。

设计取舍是用一个固定案例集中检查跨模块交互，保留失败，不建立庞大自动化平台。可能追问：“为什么不能靠真实云端取代单元测试？”回答要点：真实服务慢且有网络不确定性，难以稳定覆盖每个拒绝分支；离线测试适合程序边界，真实验收检查接入事实，两者职责不同。这里已实现并运行真实链路，但未验证生产稳定性、负载或跨账号隔离。

### 7.2 如何证明重启后读到的不是内存

业务问题是服务停止后，计划和进展是否还在。对应基础知识是进程生命周期与持久化边界。代码证据是terminate、wait、重新Popen以及API完整结果比较；报告记录进程编号和请求响应。

取舍是本机单worker、同目录SQLite，不引入分布式存储。可能追问：“这是否等于容灾？”回答要点：只验证本例的进程更替恢复；磁盘故障、备份还原、断电一致性和多实例协调没有验证。SQLite承担存储保证，个人实现负责对象关联与验收断言，不能宣称自研数据库恢复机制。

### 7.3 为什么回执重放和旧状态拒绝要一起检查

业务问题是用户不知道上次是否保存，同时另一窗口可能已经更新。对应基础知识是幂等与乐观并发。代码证据是blocked-1原请求重放返回同event_id，而新请求stale使用expected_revision=0返回409；随后原请求在新进程中仍读取原事实。

取舍是复用PlanExecutions中的唯一约束与SQLite事务，不引入消息队列或分布式锁。可能追问：“为什么不直接忽略所有重复点击？”回答要点：同编号换内容应拒绝；不同编号基于旧状态也不能无条件接受。当前只覆盖指定业务对象和请求身份，不是全系统exactly-once。

### 7.4 Agent完成率和内容质量为什么要分开

业务问题是模型返回合法候选，但可能要求做不必要的工作。对应基础知识是结构约束、来源完整性和语义评测的区别。项目证据是报告保留真实三人格意见、综合候选和冻结原文；程序断言只证明设定条件成立，内容复核独立记录。

可能追问：“引用合法能否消除幻觉？”回答要点：只能约束编号及原文来源，不能证明引用支持每条建议，也不能证明建议符合现实。融合检索、重排、更多固定质量案例是可扩展方案，当前未实现或未在本轮验证，不能提前写作收益。

### 7.5 业务完成为什么不能直接等同于框架已经停止

本轮业务问题是已保存v1但同一会话不能继续。基础知识是状态机之间的一致性和可重入恢复。真实c报告暴露失败，`WebService._sync`显式END及真实图故障测试提供修复证据。取舍是复用框架清理调度能力，并用稳定消息ID和最后才写synced构成可重复恢复，而不是修改next检查或触发额外模型调用。

可能追问：“两个数据库更新不原子怎么办？”回答要点：先保存可恢复的业务结果，最后标记同步完成；中断时按确定身份重做，不能保证跨库瞬时一致，但能恢复已知流程。已验证消息写入后END前失败的恢复；磁盘损坏、任意外部进程修改checkpoint和分布式并发未验证。依赖框架版本升级时应重跑真实图集成测试，替身无法证明调度语义。

以上是本项目可解释的基础知识，不引用具体公司考题，不虚构面试频率或性能提升。临时凭据与参数错误只留在模块总结；真实checkpoint续接修复达到核心可靠性复盘条件，单独在question.md记录证据与取舍。
