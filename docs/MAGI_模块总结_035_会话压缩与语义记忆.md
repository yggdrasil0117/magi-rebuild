# 模块035 会话压缩与跨会话记忆召回

## 从一个备考问题看两种记忆

你确认了「每周可学习10小时」，又在长会话里讨论了协程取消、示例脚本与尚未完成的验证。前者是用户确认过的约束，后者是聊天过程。打开另一个会话问「这一周最多可以投入多少时间准备面试」，系统可以按语义找回约束。继续原会话时，系统可以用旧对话摘要交代任务进展，再保留最近的对话原文。

日常网页聊天自动使用会话压缩。语义召回需要在输入框旁主动勾选「语义召回个人记忆」。启动前在项目环境安装可选依赖：

```powershell
.\.venv-harness\Scripts\python.exe -m pip install -e '.[memory]'
```

语义召回复用硅基流动 BGE-M3。当前问题和需要建立索引的已确认记忆文本会发送给该服务。勾选只适用于日常聊天，页面可展开本轮采用的记忆版本。关闭时沿用原有记忆注入规则。摘要使用会话配置中的生成模型，云端失败沿用原有失败处理。

## 摘要保留了什么

`AllowedToolBoundary.wrap_model_call` 在最终容量检查前取出模型请求的消息。文本大小超过配置容量约三分之一时，调用 `ConversationSummary.compact`。阈值用 UTF-8 字节估算，和现有守卫一致，实际 token 数取决于模型。窗口按人类消息划分，保留最近三个轮次，当前轮次也计入。工具请求和结果不会被窗口从中间切开。

`src/magi/harness/summary.py` 的关键保存逻辑如下，省略了前面的输入与输出检查。

```python
with db:
    db.execute(
        "INSERT OR REPLACE INTO summaries VALUES (?,?,?,?)",
        (self.thread_id, cutoff, self.digest(messages[:cutoff]), body),
    )
```

`thread_id` 是当前上下文版本对应的运行会话身份。更新或删除已确认记忆会沿用已有机制切换上下文，旧摘要仍属于旧 thread。`cutoff` 是摘要覆盖的消息数，`digest` 是被覆盖消息前缀的摘要哈希。重开连接时只有前缀匹配才复用。窗口向前推进时，用上次摘要加新增移出的消息生成新摘要。生成和数据库提交成功后才使用新覆盖位置。

摘要只替换发给模型的请求。原始消息仍保留在 checkpoint 和网页业务历史中。生成失败、输出截断或摘要过长时，本轮回到原请求，容量守卫继续检查。旧摘要仍留在库中，下次请求可以从旧覆盖位置继续。每轮至多尝试一次摘要生成。若一次待压缩输入已经超过摘要预算，仍可能需要新建会话。本轮未实现分批压缩，也未另加容量不足时的上下文削减策略。

## 语义召回与写入边界

SQLite 依然保存正文、作用范围、状态和版本。第 9 版迁移建立 `memory_index_pending`，并通过 SQLite 触发器在新增或修改记忆的同一事务中登记当前版本。Qdrant 本地模式把向量持久化在独立目录。两者没有跨库事务，SQLite 队列保存下一次需要处理的版本，Qdrant 目录可从业务库重建。

`src/magi/personal/recall.py` 的 `recall` 接收上下文服务、逻辑会话、当前问题和配置。它只取当前全局和会话范围内的有效记录，继承同键时会话记忆优先的规则。每次最多补建31个缺失向量，问题和记忆使用同一嵌入模型。Qdrant 按余弦相似度返回至多五项。查询还限定为当前有效版本对应的向量 ID。更新后旧向量即使尚未清理，也不在候选集合里。

索引工作成功后使用以下实际代码清理队列。省略外层事务与旧向量清理代码。

```python
db.execute(
    "DELETE FROM memory_index_pending WHERE memory_id=? AND version=?",
    (job_id, version),
)
```

`job_id` 是记忆身份，`version` 是本次完成的工作版本。假如 10 小时改成 4 小时的同时又改成 2 小时，迟到的旧工作不能清掉新版本的待办。旧向量清理也按版本范围执行。服务重启后，下一次主动启用语义召回会继续处理当前可访问范围的待办。这里采用请求触发的同步，当前没有后台常驻消费者。被会话同键覆盖的全局记录会在其他可使用它的会话中索引。

查询后再回 SQLite 验证候选。建立模型会话时还会重新检查一次：

```python
active = {(row["id"], row["version"]): row for row in memories}
memory_selection[:] = [
    active[identity]
    for row in memory_selection
    if (identity := (row["id"], row["version"])) in active
]
```

传给模型和展示给用户的都是当次检查通过的 SQLite 正文。若语义召回失败，页面显示暂不可用，本轮语义注入为空。页面记录的是已完成回复的当时用量，后续删除不会改写历史聊天。多进程同时修改记忆与模型执行期间的即时撤回没有验证。

消息 ID 标识一次网页提交。同一提交重试仍通过已有摘要检查，关闭新开关时摘要兼容升级前请求。记忆 ID 表示一个长期事实槽位，版本表示其一次变更。Qdrant 点 ID 由二者共同生成，可重复写入同一版本。

## 面试知识关联

- 上下文预算。为什么滑动窗口不能直接按最后 N 条消息切？一组工具调用和工具响应要一起保留，按完整轮次切更容易保证请求合法。代码在 `ConversationSummary.compact` 计算切点。
- 事务待办。为什么队列和业务记录一起提交？如果业务写入成功却没登记同步任务，索引可能永久遗漏新版。SQLite 触发器让两次写入共享事务。Qdrant 写入和队列确认仍是两个动作，所以点 ID 固定，队列确认带版本。
- 检索和事实权威。为什么索引已经限定版本还要查 SQLite？查询期间用户可能修改记忆。查询后和提示词组装前复核可以过滤已经失效的候选。正在生成的请求采用已组装的当轮上下文。
- 复用组件。Qdrant 负责本地持久化与相似查询，硅基流动负责向量，Deep Agents 负责模型和工具循环。MAGI 新增窗口、覆盖位置、同步事务和注入边界。

先阅读真实服务记录，再对照摘要保存和待同步队列。可以用三个问题复述：摘要生成失败后覆盖位置怎么变化？为什么旧索引点无法重新注入？如果索引已经写入却没清理待办，下一次请求会怎样？
