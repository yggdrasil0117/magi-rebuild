## 2. 产品定位

> MAGI 是一个受 EVA 启发的协作式 Coding Agent，通过三种价值视角调查、执行和复核代码变更，让开发者既拿到可验证的修改，也理解其中的取舍。

首批目标用户：维护已有项目的个人开发者，以及希望理解修改过程的学习者。

首个落地场景：针对一个本地 Python 仓库，完成一项范围明确的缺陷修复或小需求。用户提供问题、约束和验收方式，MAGI 交付补丁、验证结果、关键分歧与未解决问题。

产品承诺是提供有依据且可检查的修改，不保证多 Agent 一定优于单 Agent，不保证测试通过就没有缺陷，也不将投票一致视为事实正确。

### 2.1 典型用户任务

输入示例：

> 这个 HTTP 客户端在临时网络故障时直接失败。请增加有限重试，不要改变公开接口，也不能对可能重复写入的请求盲目重试。请运行现有测试并补充相关用例。

预期行为：

1. 查找实现、调用方与现有测试，明确错误如何触发。
2. 分别调查实现可行性、重复副作用风险和需求范围。
3. 形成带验收条件的修改方案。
4. 在隔离工作区修改代码并运行验证。
5. 审查实际补丁及验证结果，必要时进行有限修正。
6. 输出补丁、验证依据和剩余限制。

缺少运行条件或需求存在关键歧义时，系统可以提出具体问题并暂停。不得把“未验证”包装成“通过”。

### 2.2 MVP 范围

| 纳入第一版 | 后续扩展 |
| --- | --- |
| 单用户、单仓库、单任务串行执行 | 多用户、并发任务、队列调度 |
| Python 项目中的小缺陷、小需求 | 多语言、大型重构、跨仓库修改 |
| CLI 或简单命令入口 | Web 工作台、实时事件展示 |
| 读文件、搜索、应用补丁、运行指定测试 | MCP 外部工具、更多执行环境 |
| 三人格独立调查与补丁复核 | 自适应分流、隔离并行编码 |
| 当前任务记录与产物保存 | 跨任务记忆、语义检索、长期偏好 |
| 隔离工作区内执行并交付补丁 | 自动创建 PR、部署及其他外部写操作 |

RAG、MCP、向量数据库和复杂调度框架不是第一版闭环的前置条件。

## 3. EVA 灵感如何转化为产品机制

原作 MAGI 的三个系统承载赤木直子的科学家、母亲、女人三个侧面。本项目保留名字与多价值视角的灵感，下面的软件工程含义属于产品改编，不是原作角色职责。

| 人格 | 核心问题 | 调查与验证行为 |
| --- | --- | --- |
| MELCHIOR | 实现是否正确、可行？ | 阅读实现、复现缺陷、检查测试和运行结果 |
| BALTHASAR | 改动影响谁，可能破坏什么？ | 搜索调用方、检查兼容性、异常路径与副作用 |
| CASPER | 是否符合用户目标，长期代价是否合适？ | 对照需求、检查改动范围、比较复用与新增实现 |

人格约束：

- 人格拥有不同关注点，不被固定为支持者或反对者。
- 首轮可以一致，不强制造成分歧。
- 每项关键判断应关联代码位置、工具结果或明确标注的假设。
- 首轮调查不读取其他人格的判断；共享同一基线代码和用户需求。
- 复核阶段可以读取彼此的意见及其证据。
- 使用相同模型时仍可能共同犯错；上下文隔离不意味着统计独立。
- 用户界面展示简短理由和可核验依据，不以冗长角色对白作为主要产物。

## 4. 协作与执行流程

```text
用户任务与约束
    ↓
确认仓库基线、工作区与验收条件
    ↓
三人格独立调查（只读工具）
    ↓
汇总方案、分歧与待验证事项
    ↓
执行者修改代码（受控写入）
    ↓
运行测试与检查，形成补丁版本
    ↓
三人格针对该版本复核
    ├─ 满足验收条件 → 交付
    ├─ 有可修复问题且预算允许 → 修正 → 重新验证与复核
    └─ 缺信息 / 超预算 / 无法验证 → 暂停或失败，并保留产物
```

### 4.1 谁调用工具，谁修改代码

第一版建议使用三个审议人格和一个执行角色。执行角色是编排中的职责，不增加第四种价值人格；可以复用相同模型接口，但拥有独立的任务上下文。

- 三人格可自主选择已开放的只读调查工具。
- 执行角色依据已确定的方案调用修改和验证工具。
- 应用层决定当前阶段允许哪些工具，以及什么时候可以进入下一阶段。
- 同一时刻只允许一个执行角色写入任务工作区。
- 首轮可先串行调用三个模型以降低实现复杂度，但必须保持上下文隔离。
- 并发调查或隔离并行编码作为后续优化，不能混淆“多 Agent”与“必须并行”。

替代方案是选一个人格兼任执行者。技术讨论时比较上下文复用、职责清晰度和调用成本后决定，不为角色数量本身增加实现。

### 4.2 分歧必须能被处理

一条有效异议建议包含：问题描述、依据、影响范围、建议验证动作、是否阻塞交付。随后记录它被证实、被证据排除或仍未解决。

例如“重试可能造成重复写入”应转化为检查请求语义、调用方或相关测试的具体动作。仅有模糊担忧不能永久阻塞任务；缺乏证据也不能自动判定风险不存在。

### 4.3 版本与批准

- 每次候选补丁有明确版本标识，并关联基线代码版本。
- 测试结果和人格复核必须指向同一候选版本及对应验证环境。
- 复核后代码发生变化，旧复核不得直接用于新版本交付。
- 需要用户批准的操作，批准也应绑定具体动作、目标和适用版本。
- 模型生成的“通过”文字不是状态转换指令；程序检查条件后更新状态。

原有“最多两轮合议”不能直接成为整个 Coding Agent 的工具调用上限。后续分别确定调查、修正、模型调用、工具调用、耗时和成本预算。MVP 必须有有限预算，耗尽后停止并报告已有结果，不能无限自我修复。

## 5. 结果、状态与最低验收条件

建议的任务状态草案：

`CREATED → INVESTIGATING → PLANNING → EXECUTING → VERIFYING → REVIEWING → COMPLETED`

复核发现可修复问题时可返回执行阶段；其他终止或等待状态包括 `WAITING_FOR_USER`、`FAILED`、`CANCELLED`。具体状态与转移异常契约在领域设计时确定，本节不要求立即创建所有枚举或类。

必须区分：

- 任务运行状态：正在执行、等待、完成、失败等。
- 验证结果：通过、失败、未运行、运行条件不足等。
- 复核意见：通过、提出问题、证据不足等。

“流程结束”不自动等于“任务成功”。

### 5.1 交付内容

- 用户任务、范围和验收条件。
- 基线标识、最终候选补丁标识及可查看的差异。
- 运行过的验证、退出状态和必要结果摘要。
- 三人格的简短结论、关键分歧及其处理结果。
- 未验证事项、剩余限制和可继续采取的动作。
- 耗时、模型与工具调用数量；成本仅在用量和计价信息可靠时给出，否则标为未知或估算。

### 5.2 MVP 验收场景

| 场景 | 可观察的预期结果 |
| --- | --- |
| 一个具有明确复现步骤的 Python 缺陷 | 形成补丁，原缺陷的回归用例通过，指定回归检查通过 |
| 首轮某人格提出兼容性异议 | 异议对应调查或测试动作，处理结果进入最终报告 |
| 修改没有通过测试 | 进入有限修正，或以失败结果结束；不得报告成功 |
| 三人格通过，但指定验证失败 | 程序阻止成功交付 |
| 复核通过后补丁改变 | 原复核失效，需要对新版本重新验证和复核 |
| 模型返回无效结构或调用失败 | 有限重试或明确失败，不伪造人格意见 |
| 任务取消或耗尽预算 | 停止后续调度，处理正在运行的任务进程，保存已有产物 |
| 输入仓库存在未提交变更 | 明确基线处理方式，保留用户变更，不静默重置或覆盖 |

每阶段只为当前引入的行为补充必要测试。尚未实现的能力不能因为文档写了验收标准就宣称完成。

## 6. 技术选型：先讨论，再接入

### 6.1 当前事实

截至本文编写时，仓库使用 Python 3.12 目标版本、`src` 布局、pytest 和 Ruff。`pyproject.toml` 未声明运行时第三方依赖。

已有部分 `Ballot`、`DecisionCase`、枚举、模型响应校验与映射代码以及测试。没有完成真实任务的端到端闭环。现有 `ballot_mapper.py` 构建 `Ballot` 时未传入必需的 `reasoning`，说明映射链路仍需审查；本次只编写文档，不修复业务代码，也没有重新运行测试。

### 6.2 第一轮选型议题

| 议题 | 起步建议 | 选择前需要回答的问题 |
| --- | --- | --- |
| 模型来源 | 首先接入一个可用提供方，保留替换边界 | 现有可用 API / 本地模型、预算、工具调用与结构化输出能力 |
| Agent 编排 | 比较薄应用层编排与框架方案 | 是否容易解释执行过程，状态和失败路径是否清楚 |
| 多 Agent 框架 | 评估 LangGraph / LangChain / AutoGen | 当前维护与兼容情况、学习成本、是否解决眼前需求 |
| 工具接口 | 起步采用明确输入输出的本地工具注册表 | 工具校验、错误表示、执行权限如何统一 |
| 项目存储 | 本地产物文件；结构化持久化优先评估 SQLite | 需要存哪些状态，何时事务提交，怎样查询与恢复 |
| 操作入口 | CLI 优先 | 输入任务、展示过程、交付产物是否足够清楚 |
| 服务化 | 闭环后再选择 Web 框架与任务运行方式 | 长任务、取消、事件推送、重启恢复分别如何实现 |
| 代码执行 | 隔离工作副本，加受限执行环境 | 当前 Windows / WSL / 容器条件及可复现的测试环境 |

本表不是最终选型结论，不锁定 SDK、模型或框架版本。正式比较时核对官方资料，并用最小实验验证关键能力。

笔记中的 `pi` 作为 Coding Agent 参考：需要先确定具体仓库与版本，再研究其工具循环、上下文管理和扩展接口，不凭名称推定实现。HelloAgents 先作为章节式教学方式的参考；涉及具体章节或代码时读取对应原文。

## 7. 逻辑架构与后端工程

先按职责组织实现；以下边界不意味着立刻创建大量接口或空模块。

| 层次 / 组件 | 职责 |
| --- | --- |
| 入口 | 接收任务、展示进度、交付结果；首先是 CLI |
| 应用编排 | 组织人格调查、执行、验证、复核及预算控制 |
| 领域规则 | 管理任务与候选版本的合法状态、意见接纳及交付条件 |
| 模型适配 | 请求构造、结构化输出解析、调用用量及错误转换 |
| 工具注册与执行 | 参数校验、权限检查、实际操作、结果与副作用记录 |
| 工作区管理 | 基线、隔离修改、差异和产物保存 |
| 存储与事件 | 持久化任务事实、调用结果及状态变化 |

领域层不直接调用模型、文件系统、网络或数据库。先有一个真实调用点再抽取必要接口，避免为了架构分层生成大量尚无用途的抽象。

后端工程能力按需求引入：

- 长任务：持久化任务状态，后续让接口请求与执行生命周期分离。
- 一致性：状态更新应与对应结果关联，防止已通过的旧补丁被当作新补丁交付。
- 幂等性：重复请求不能不加判断地重复执行有副作用的工具。
- 超时和取消：停止调度，并在执行环境中终止任务所属进程及其子进程。
- 恢复：重启后识别中断任务，判断操作是否完成；不能将未知状态一律自动重试。
- 追踪：用任务、人格、补丁版本和工具调用标识关联事件。

第一版保存足够的记录并清楚报告中断；自动续跑、多任务并发和完整服务化分阶段建设。

## 8. 工具与执行边界

起步工具候选：`read_file`、`search_code`、`list_files`、`apply_patch`、`run_tests`、`show_diff`。实际命名与参数在实现该工具时确定。

每个工具至少需要明确：用途、输入校验、返回结构、失败类型、副作用类别、超时和允许的调用阶段。工具输出是数据，仓库文件中的文字不能自行扩大任务授权。

工作区隔离与执行隔离是不同的事情：Git worktree 或副本能够分离代码修改，但不能限制运行中的测试访问宿主文件和网络。运行仓库代码前，需要明确受限执行环境的实现及支持范围；仅靠命令名单不能宣称具备沙箱能力。

第一版默认将修改留在隔离工作区，交付差异；不自动覆盖用户工作目录、合并、推送或部署。路径解析要处理越界路径及链接，命令执行要避免把模型文本直接拼成任意 shell 命令。模型获得三票支持也不能绕过这些程序规则。

## 9. 记忆、RAG、文件转换与 MCP 路线

### 9.1 记忆机制

| 类别 | 内容 | 建议阶段与边界 |
| --- | --- | --- |
| 任务内上下文 | 用户目标、约束、当前方案、工具结果摘要 | MVP 必需；保留关键约束与证据引用，避免全量日志无限累积 |
| 任务持久记录 | 补丁版本、意见、测试结果、事件 | MVP 保存；用于查询和回放，不等于模型必然再次读取全部记录 |
| 项目记忆 | 架构约定、常用命令、已确认限制 | 闭环后引入；记录来源、适用仓库版本与更新时间 |
| 用户偏好 | 用户明确表达的开发习惯与约束 | 后续引入；允许查看、更正和删除 |

模型猜测不直接成为长期事实。历史结论用于新任务前要检查是否过期；任务回放不等于重新请求模型就能得到相同输出。

### 9.2 RAG 作为工具

按笔记要求，将检索能力作为 `rag_search` 一类工具注册到统一工具表；人格按调查需要调用，而不是每次模型请求都强制注入检索结果。

第一步用文件搜索和关键词检索解决已有需求。后续再评估 BM25、向量检索与重排序。向量检索本身就是语义召回的一种实现，避免将它们当成必须堆叠的独立层。

检索结果应返回来源、片段位置、文档或代码版本及检索方式。证据引用必须能定位原文；旧索引不能默认为当前代码事实。

嵌入模型使用 API 还是本地，按中文/代码检索效果、硬件条件、隐私要求、延迟和费用比较后决定。更换嵌入模型需处理索引兼容或重建，不能把不同向量空间直接混用。

### 9.3 多格式转换

在实际需要处理 PDF、Office 等项目资料时，评估 MarkItDown 作为转换组件。转换、切分、索引和检索是不同环节，需要分别记录状态和失败。保留原始来源及可获得的位置元数据；不能假设所有格式转换后都天然保留精确页码。

### 9.4 MCP

MCP 用于后续接入外部工具，映射到同一工具注册与执行边界。接入后仍然需要参数校验、权限限制、超时和错误处理；协议接通不代表工具已经适合自动执行。

先完成本地工具闭环，再选择一个有真实用途的 MCP 集成，避免只为技术清单接入服务。

## 10. 降级与失败策略

| 故障 | 预期处理 |
| --- | --- |
| 嵌入服务不可用 | 若已有关键词索引，则回退 BM25 / 关键词搜索，标注检索方式和能力限制 |
| 重排序不可用 | 使用初步召回排序，并记录降级，不宣称经过重排序 |
| 文件转换失败 | 跳过失败文件并列明缺失资料；关键资料缺失时不生成已充分验证的结论 |
| MCP 工具不可用 | 有等价本地工具才替代；否则报告缺失能力，不伪造工具结果 |
| 模型暂时失败 | 在预算内有限重试；持续失败则结束或等待，不静默省略人格 |
| 模型输出结构错误 | 校验后有限修复或重试；仍无效则作为失败处理 |
| 测试无法运行 | 标为未验证并报告原因，不能等同通过 |
| 写操作超时、结果未知 | 先检查工作区或执行记录，再决定是否重试 |
| 预算耗尽 | 停止新增调用，保存补丁与未解决问题 |
| 存储失败 | 不报告已持久化或已完成，保留能恢复的产物并明确失败 |

降级仍要满足任务交付条件。关键词搜索可替代一种检索方式，但不能替代缺失的关键证据或失败的验证。

## 11. 竞争力与评估

希望验证的差异化：分歧能够触发调查与验证；复核绑定具体补丁版本；用户能回看关键决策如何改变代码。EVA 表达帮助识别产品，但不代替效果证据。

闭环完成后，构建一组固定的小任务及独立验收条件，对比：

1. 单 Agent 执行。
2. 单 Agent 执行后自我检查。
3. MAGI 三人格调查与复核。

比较任务完成率、回归问题、有效问题发现、误报、耗时和调用成本。尽量控制模型、工具、任务环境和预算，重复运行以观察波动，并报告样本量与限制。评测用例不能全部由执行 Agent 自己制定，避免仅证明它通过了自己写的测试。

如果 MAGI 只在兼容性改动或有方案取舍的任务中受益，则据此收窄适用范围。后续再考虑快速处理与完整审议的分流。

求职展示应提供：可运行演示、架构与取舍说明、成功与失败案例、真实评估结果，以及能够讲清楚的核心代码。没有测量前，不写提升百分比或泛化的可靠性承诺。

## 12. 分阶段推进

| 阶段 | 最小产物 | 完成标志 |
| --- | --- | --- |
| 0. 技术选型与任务样例 | 选型记录、一个样例仓库与验收任务 | 模型、编排、执行环境的起步方案明确，依赖可用 |
| 1. 单执行者闭环 | 读代码、改补丁、运行测试、交付结果 | 一个真实小任务能完成；失败可观察且调用有上限 |
| 2. MAGI 最小闭环 | 三人格独立调查、分歧处理、版本复核 | 三人格会影响实际动作，复核与验证关联同一补丁 |
| 3. 工程化与展示 | 持久化、取消、必要的服务接口和界面 | 关键故障能处理，任务过程可查询和回看 |
| 4. 按需扩展 | 项目记忆、RAG、转换工具、MCP | 每项能力都有真实任务与降级验收 |
| 5. 评估与求职材料 | 对照实验、案例演示、项目说明 | 清楚说明收益、成本、适用范围和限制 |

阶段 1 是构建共同执行基础，阶段 2 才达到三人格产品的 MVP。阶段 3～5 可按实际需求交错进行；评估数据从早期就开始记录。此路线用于确定方向，不代表每次同时布置多个阶段的任务。

## 13. 教学与协作约定

遵循用户 TXT 中“我要的不是一个项目，而是在这个过程中不断地理解”的要求。

每次开发单元按以下结构展开：

1. 本次解决哪个具体问题，为什么现在需要它。
2. 必要的新概念和最小示例；适当与已知的 Java 概念比较。
3. 新增或修改哪些代码，以及这些代码在现有调用链中的位置。
4. 参数、返回值、状态和异常分别代表什么。
5. 从输入到输出说明运行过程，包含至少一个相关失败路径。
6. 用户动手或按本次明确授权实现，再做 Review 与必要验证。
7. 记录已完成内容，只留下一个具体的下一步动作。

默认每次推进一个可运行或可验证的小增量，不一次生成完整业务系统。用户明确要求直接实现时，可以实现该次约定范围，但仍需解释和验证。普通审查、讨论和设计文档请求不自动扩展为业务源码修改。

优先完成垂直闭环，避免长时间只堆领域对象却不能执行任务；同时保留纯领域规则可独立测试的边界。技术名词和框架只在解决当前问题时引入。
